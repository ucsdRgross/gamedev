⚠ WHY THE SUITE IS GREEN AND THE GAME IS BROKEN — understand this before coding.
Every Main-based test writes `get_tree().paused = false` right after add_child().
The real game NEVER does: §1.6 holds the tree paused for the whole session. That
single habit hid all three criticals. PICTURE_WALL.md documents the unpause as
mandatory in tests — that note IS the mask. Any test you write for these must

=== CRITICAL 1 — the app soft-locks on the first Wall press ===
`Main` has no process_mode, so it is PAUSABLE; a tween bound to a PAUSABLE node
under a paused tree never advances. `_animate_camera()` awaited exactly such a
tween: `_move_in_flight` and `input_locked` stick true forever and every handler
dead-ends. Only Alt+F4 exits. Reachable from Wall, New Run, Back-falling-through,
the Info toggle, and wall-view→picture entry.
PARTLY FIXED (09d3110): that tween now uses `camera.create_tween()` (%Camera2D is
PROCESS_MODE_ALWAYS), matching WallTransition.
NOT FIXED: a regression test that leaves the tree paused STILL HANGS THE SUITE, so
at least one more await in that path does not survive a paused tree. FIND IT.
Start by writing that test (a real Main, no unpause, focus a picture then
_go_to_wall_view, assert it completes and _move_in_flight clears), watch it hang,
then bisect the awaits in _focus_picture / _go_to_wall_view / _animate_camera /
the music crossfade loop. This is the first thing to fix; nothing else matters
until the game runs.

=== CRITICAL 2 — Pacing.wait() never fires in the shipped game ===
SceneTreeTimer has NO node binding: `process_always = false` keys on the TREE's
pause flag, which §1.6 holds permanently on, so a PROCESS_MODE_ALWAYS screen root
does NOT rescue its timers. Measured: time_left does not move at all while paused.
game.gd's scoring cascade awaits one, so a hand stalls mid-reveal forever.
⚠ This means S6's entire create_timer sweep made the game WORSE, and
TestWallPause's U5 asserts the broken behaviour AS CORRECT.
The fix is a design decision, so read D6/Q75=b first and file a gap if two options
differ observably. The likely answer: a node-bound `Timer` child respects
process_mode and freezes with its own screen, which is what D6 actually wanted —
SceneTreeTimer cannot distinguish "frozen screen" from "paused tree" because it
only ever sees the tree.

=== CRITICAL 3 — reduced motion rests at wide zoom ===
sample_at()'s reduced branch returns _wide_zoom for EVERY elapsed including the
last, and nothing re-poses the camera after, so each destination rests at ~0.44
zoom instead of ~1.11 with its frame visible, compounding every transition.
Violates H3/Q27/S37 ("no frame is ever visible at rest"). T12 asserts the final
POSITION but never the final ZOOM — add that clause.

=== MAJOR 4 — the frame nine-slice never applies in the real game ===
wall_picture.gd gates patch_margin_* on `entry.frame_texture ==
shared_frame_texture()`, which is REFERENCE identity. The texture loaded from
layout_default.tres is a different instance, so the branch is always false and the
40x40 bevel smears across a ~1330x745 NinePatchRect. Introduced by C6 (the game
now loads the .tres). Every by-eye fixture assigns the shared texture directly,
which is why snapshots look right and the product does not. Gate on something
real (size/flag/metadata), not identity.

=== MAJOR 5 — Back/Forward desynchronise the focus stack ===
_focus_stack.back() mutates history BEFORE _focus_picture's `if _move_in_flight:
return` guard, and neither entry point is gated during a move. Double-press Back
and the stack loses an entry permanently: Back greys out while a picture is still
behind you. Q56=b says a new destination is IGNORED, not half-applied. Gate the
handlers, not just the mover.

=== MAJOR 6 — the Info toggle has no re-entrancy guard ===
_on_info_toggled awaits _animate_camera without checking or setting
_move_in_flight, so it fights a live transition and settles on the SOURCE
picture's info pose. Also unhandled by _on_window_resized.
