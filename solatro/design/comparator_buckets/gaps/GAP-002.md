# GAP-002 — the uncapped straight search reached 23 s for ONE scoring pass
status: withdrawn
outcome: withdrawn
withdrawn: 2026-08-10 — **IT WAS NEVER A GAP. IT WAS AN IMPLEMENTATION BUG, AND THE DESIGN WAS
  RIGHT.** The owner pushed back on the premise — *"ideally it is near instant with O(n) runtime.
  i dont understand how it can take so long"* — and the pushback was correct. `_finalize_rank_class`
  derived a class's `member_keys` from the union of its MEMBERS' VALUES. A card carrying an extra
  rank value (§1.7) sits in SEVERAL classes at once, one per value, so its second value leaked into
  every class holding it and marked them all `mixed`. §1.5's search is
  `prod(member_keys.size())` over mixed classes, so eight dual-value cards produced **2^16 = 65536**
  straight scans where the design specifies **1**. §1.5's own words — *"the product … is 1 when no
  rule merged anything"* — were the specification, and the code violated it.
  **Fix, in two halves — the same mistake at both stages.**
  (1) **Stage 0:** a class OWNS its positions. Seeded with the key it was created at, unioned only
  when two classes genuinely MERGE, narrowed at finalize to the keys its members still sit at.
  (2) **Stage 1:** `_rebuild_classes` seeded a group's keys from `rank_values_of`, so a
  SINGLETONISED group — one card, merged with nothing — came out `mixed` with one key per extra
  value: three values on eight cards is 3^8 scans. It seeds from `get_rank_profile` (printed
  values) now, and `mixed` is decided on printed values throughout, which is what §1.4 says it
  means: *"true when members do NOT share one printed value"*. A class may occupy several
  positions without being mixed; only a DISAGREEMENT between members costs a cartesian factor.
  Measured: **23156 ms → 1854 ms** after half one, **→ 23–50 ms** after half two, stable across
  six consecutive runs.
  Pinned by `test_comparator.gd` section 11, which asserts the assignment count directly — the
  failure mode was invisible in results, since every score was correct, just astronomically slow.
  ⚠ Nothing in the design or the plan needed to change. `PLAN.md` §5 and `DEFERRED.md` E2 still
  record the search as uncapped and unmeasured on a real board; that remains true and unaddressed.
raised: 2026-08-10, during plan step S19 (the mod-space fuzz)
design: DESIGN.md version 1, nodes F5, F8, Q96; PLAN.md §1.5, §5; DEFERRED.md E1, E2
severity: GAP

**What the design says** — `PLAN.md` §1.5, verbatim: *"The product is `prod(member_keys.size())` over
mixed classes only, and is **1 when no rule merged anything** … There is **no cap**: if a real board
ever makes this expensive, **that is a gap to file, not a bound to invent**."* §5 records the same
thing as an accepted risk: *"The straight search has no cap … Bounded in practice by thirteen
positions and by how many mixed classes a board holds; **unmeasured**, because no benchmark exists
for the scoring path."*

**What the ANSWER says** — Q96(c) is what creates the search: a mixed class acts as *"any one of its
members' positions, whichever makes the longest run"*, and DESIGN §8 flags the cost in the owner's
own summary — *"Q96(c) turns the straight scan from a single walk into a **search** … It is bounded
— thirteen positions, few merged groups — but it is not the linear scan the code has today."* That
says the cost exists and is bounded; it does not say what to do when the bound is reached, and
§1.5 explicitly routes that here instead of letting the executor pick a number.

**What it does not say** — what to do now that it HAS been reached: cap the search, make it cheaper,
or accept it.

**Why it blocks** — triage test (2): it is an owner call, and the options differ in observable
behaviour (a cap can make a legitimate straight go unfound). Measured on Box A, **sole occupancy**,
`Tests/Engine/test_mod_fuzz.gd` seed `6878345430599174237`:

    slowest scoring pass: 23156 ms — 8 cards,
    rules ["R0(h0 d2 p5 s1)", "R1(h0 d0 p0 s8)", "R2(h5 d2 p0 s9)"], order [1, 2, 0]

**23.2 seconds for one `PokerHands.score` call on an EIGHT-CARD hand.** The rule set is two meld-deny
rules and one extra-rank-values rule — nothing re-entrant, nothing pathological, no rule that is
itself slow.

⚠ **Reproducible, not a one-off.** Slowest pass across six consecutive sole-occupancy runs, each at
a fresh random seed: **143 ms · 1208 ms · 314 ms · 23156 ms · 59 ms · 22167 ms**. Two of six runs
exceeded 20 s. The distribution has a very long tail rather than a uniform cost, which is the
signature of a combinatorial term that is usually 1 and occasionally large — exactly the shape §1.5
predicted and left uncapped.

⚠ **A submit that takes 23 s is indistinguishable from a hang to the player**, and R1 already
accepts that a grouping rule may genuinely hang one. This is the same symptom arriving without any
of R1's causes.

Two multipliers compound, and which one dominates is not yet measured:
- **the cartesian product itself** (§1.5) — `prod(member_keys.size())` over mixed classes, and
  `on_meld_extra_rank_values` (Q71=c) enlarges `member_keys` without merging anything;
- **the profile rebuild count** (DEFERRED E3, Q57=a) — the straight handlers build a profile per
  suit bucket per extraction iteration, over two paths, and every one of those now re-runs stage 0
  and stage 1 and then re-runs the search.

**Options I can see** — **(a)** cap the assignment count and fall back to the lowest-member position
for the classes beyond it — cheapest, and a legitimate straight can silently go unfound, which is
the shape Q33 already warns reads as a scoring bug · **(b)** make the search cheaper rather than
bounded: memoise per position set, or solve the longest run over candidate positions directly
instead of enumerating assignments — no behaviour change, real work, and no number invented ·
**(c)** cap the INPUT instead of the search: a limit on how many member_keys one class may offer,
which is a content-facing rule a card author can reason about · **(d)** accept it and do E3 first,
on the theory that the rebuild count is the real multiplier and the product is fine once the search
runs a handful of times instead of dozens · *my recommendation* (d) then (b) — E1 (a benchmark for
the scoring path) is what tells you which multiplier dominates, and every other option is a number
invented before the measurement that would justify it.

**Blast radius** — `Scoring.MultiStraightHandler._straight_assignments` / `_positions_for` /
`_best_sequence_from_profiles`; plan steps S12, S13; design nodes F5, F8, Q96, Q71; DEFERRED E1, E2,
E3. No behaviour outside the straight scanners changes under any option except (a) and (c).

**Meanwhile** — nothing is parked; the feature is complete and correct. `test_mod_fuzz.gd` prints the
slowest pass every run so the number stays visible, and invariant 12's bound sits at 30 s, which is
a HANG detector and deliberately not a performance budget. ⚠ **Do not "fix" this by raising that
bound.**
