# GAP-003 — a rule's answer is fixed for the HAND, so nothing needs an opt-out
status: resolved
outcome: answered
answer: Owner ruling, 2026-08-10, verbatim: *"i realize a random rule not being cached per hand makes
  no sense. If a hand is chosen and is about to be scored, the random rule should already have been
  decided before the meld finding happens. Its not like the random rule will change whether looking
  for a straight vs flush or whatever. In that case, all rules can be cached always and be
  deterministic per hand, no need for some cases to be uncached."*
  ⚠ **This SUPERSEDES Q41(c), Q90(a) and Q91(a)**, and retires `DEFERRED.md` R5.
raised: 2026-08-10, after S20, by the owner
design: DESIGN.md version 1, nodes I2, I3, I4, I8; Q40, Q41, Q90, Q91; PLAN.md §1.8
severity: CONTRADICTION

**What the design said** — Q41(c): *"cache everything by default, and let a card that consults
randomness declare itself uncacheable"*, with Q90(a) making that a property read once per board
revision and Q91(a) accepting that a card which forgets it *"gets a stale answer for the rest of the
board revision — a content bug, like any other"*. `PLAN.md` §1.8 built the cache on the BOARD
REVISION, and chart I is drawn around the opt-out.

**What was wrong with it** — the scope. A board revision spans many scored lines, so a verdict cached
at that scope pins a rule's answer across *different hands*; and one scored line rebuilds its profile
several times (DEFERRED E3), so an UNCACHED rule could answer differently **within a single hand** —
giving the straight scan and the flush scan two different partitions of the same cards. Both failure
modes come from the same mistake: the cache was scoped to the board when the question is scoped to
the hand.

**The answer** — the unit is the SCORING PASS. Every rule is asked at most once per distinct key pair
per hand, and its answer is fixed for that hand. A rule that consults randomness has therefore
already been decided before meld finding starts, exactly as the owner says, so:
- **`compare_uncacheable` is deleted.** There is no case that needs to opt out.
- **The per-revision verdict cache, its spotlight-epoch key and the never-cache rule for base
  environments are all deleted with it.** They existed only to make a board-scoped cache safe.
- **Caching is now unconditional and identical in every environment.** ⚠ That is a real gain the old
  design could not have: base environments (tests, the map) returned an empty revision key and so
  cached *nothing*, which meant the test suite exercised a code path the game never took.

**What this does NOT change** — the SE1 implementer cache (`_compare_implementers`, "does anything
implement this hook") stays keyed on the board revision. That is a different question with a
different lifetime, and it was never part of the opt-out.

**Blast radius** — plan step S6 and `PLAN.md` §1.8; `DESIGN.md` chart I nodes I2/I3/I4/I8 and
Q41/Q90/Q91; `DEFERRED.md` R5 (retired); `CardModifier.compare_uncacheable` (deleted);
`CardEnvironment.compare_cache_get` / `compare_cache_put` / `_hook_is_cacheable` /
`_pair_cache*` / `_spotlight_epoch` (deleted); `PipComparator` gains the pass memo;
`test_comparator.gd` section 8 and `test_mod_fuzz.gd`'s cacheability axis.
