# GAP-001 — can stage 0 split two cards that print the SAME value?
status: resolved
outcome: answered
answer: (b) — the closure asks each self-pair (k, k); a deny answering true shatters that key's
  cards apart. Owner, 2026-08-09, verbatim: *"yes split can split two cards with same values."*
  ⚠ **GATE 2's stated ceiling moves with it: `k(k+1)/2`, not `k(k-1)/2`.** PLAN.md §2 carries the
  correction and cites this file; DESIGN.md §1d's 78 / 10 become 91 / 15.
raised: 2026-08-09, during plan step S5 (the closure)
design: DESIGN.md version 1, nodes D3, Q1, Q4, Q82, QR2; PLAN.md §1.2, §1.4, S5, GATE 2
severity: CONTRADICTION

**What the design says** — Q82(a): a deny rule *"may forbid a pairing that printed values already
make the same — splitting two ordinary 7s"*, and chart node D3 restates it: *"FORBIDDEN: not the
same, even when printed values match (Q82=a)"*. QR2(a) and Q4(a) grant the same power. PLAN §1.4
builds `RankClass` as a LIST precisely so *"two classes may carry the same printed value"*, and §3
lists **`DenyTwoSevens` — a deny rule splitting printed-same cards (Q82)** under **Stage 0**.

**What the ANSWER says** — Q1(a), verbatim option text: *"one — pips printing the same value are
interchangeable to whoever is asked"*, i.e. the question is asked once per printed VALUE, not per
pip. PLAN §1.2 restates it as *"Asked once per DISTINCT PRINTED VALUE PAIR, never per card pair"*,
and S5 specifies the closure as *"Transitive closure over **distinct keys**, one representative pip
per key"*. None of these settles whether the closure also asks the **self-pair** (k, k) — the only
question at stage 0 whose answer could split cards sharing one key. Q1 says a rule cannot tell two
7s apart; it does not say the engine never asks whether 7s hold together.

**What it does not say** — whether the stage-0 closure asks `pair_is_same(rep_k, rep_k)` once per
key, so that a deny rule can shatter a same-value class.

**Why it blocks** — triage test (3): the plan contradicts itself, and the contradiction is
arithmetic, not interpretive. **GATE 2 is normative and states the ceiling as `k(k−1)/2` for k
distinct keys.** That is exactly the count of unordered pairs of DISTINCT keys — it excludes
self-pairs. DESIGN §1d independently fixes the same numbers (*"a hard ceiling of 78 and 10"* =
13·12/2 and 5·4/2). Asking self-pairs makes it `k(k+1)/2` — 91 and 15 — so the gate a Phase-2
implementation must self-check and the test roster's own stage-0 double cannot both be satisfied.
The two readings differ in observable behaviour (three 7s are one trip, or three separate loners),
so this is not a documentation bug I may fix against a source.

**Options I can see** — **(a)** the closure asks distinct key pairs only; splitting cards that print
the same value is **stage 1's** job (a whole-hand rule naming the cards), and `DenyTwoSevens` moves
out of the stage-0 roster — GATE 2's ceiling stands unchanged, and no rule can express "these two 7s
are different" pairwise · **(b)** the closure also asks each self-pair (k, k); a deny answering true
shatters that key's class into one class per card (forced by Q1: all its members are
interchangeable, so no two may share a class) — `DenyTwoSevens` works at stage 0 and **GATE 2's
ceiling is restated as `k(k+1)/2`** · **(c)** as (b), but the self-pair is asked only when the hand
actually holds two or more cards at that key — same behaviour as (b), a ceiling that varies with the
hand rather than a stated formula · *my recommendation* (b), because Q82 and D3 both describe the
split in pairwise language and (a) leaves an answered question with no mechanism, but the ceiling
line is normative and only the owner can move it.

**Blast radius** — plan steps S5, S15 (`DenyTwoSevens`), GATE 2's stated bound; design nodes D3,
Q1, Q4, Q82, QR2. Phase 4's straight model is untouched either way: a split class is same-value, so
Q95(a) governs it and Q96 does not.

**Meanwhile** — unparked. The closure now asks `pair_is_same(rep_k, rep_k)` once per key, before the
cross pairs, and the split is applied AFTER the merge so a deny beats a merge — the same precedence
Q94(a) gives it over a sanitize union.

**What the answer still did not settle** — one card may print a denied value while sitting in a class
a merge rule built, so "no two 7s share a class" and "7s and 8s are one class" can both be live at
once. The answer forces the plain case exactly (three 7s, nothing merged, one class each) and leaves
the collision open. Shipped rule, recorded in `ASSUMPTIONS.md`: cards are distributed into sub-classes
in hand order, each taking the first sub-class holding no card it shares a denied value with. That
satisfies every deny exactly, keeps the class count minimal, is deterministic, and leaves cards whose
values were never denied together — a deny forbids the pairing it was asked about and nothing else.
