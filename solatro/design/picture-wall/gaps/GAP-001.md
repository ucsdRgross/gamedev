# GAP-001 — SubViewportContainer is not built to be scaled by a camera
status: resolved
outcome: answered
raised: 2026-08-15, during the post-chart engine verification pass
design: DESIGN.md version 3, nodes B5, I1, H3
severity: CONTRADICTION
resolution: |
  Answered (b) in chat: drop `SubViewportContainer`. Each picture is a `Sprite2D` carrying a
  `ViewportTexture`, which is the documented way to put a viewport in world space and carries no
  distortion warning, and input is routed with `SubViewport.push_input()` plus `make_input_local()`.
  The spike in (a) is not taken — the class documentation was warning enough.

  ⚠ This answer removes `SubViewportContainer` from the design entirely, and with it
  `stretch = true`, `stretch_shrink` and `mouse_target`. GAP-002 was answered (a) — "use
  `stretch_shrink`" — which this makes impossible; see GAP-002's own resolution for how its intent
  is carried over.

  Design v5: node B5 becomes a `Sprite2D`; chart I is re-derived around manual input routing.

**What the design says** — `Q94`=(a), charted as **I1**: *"a `SubViewportContainer` under the camera,
letting Godot transform the events"*. I recommended it because it is "the engine's supported path"
and "far less code" than pushing events manually.

**What the ANSWER says** — `Q94` was answered (a) with no note. The answer took my recommendation at
face value, and the recommendation was not checked against the class documentation.

**What the docs say** —
[SubViewportContainer](https://docs.godotengine.org/en/stable/classes/class_subviewportcontainer.html)
states outright:

> *"Changing a SubViewportContainer's `Control.scale` will cause its contents to appear distorted. To
> change its visual size without causing distortion, adjust the node's margins instead."*

It is a `Control` designed to sit at 1:1 in UI space. The whole shell is a camera continuously
scaling every picture. `Camera2D` applies a *canvas* transform rather than `Control.scale`, so this
is not a proven failure — but it is the engine telling us this node is not meant to be scaled, and
[godot-proposals#4342](https://github.com/godotengine/godot-proposals/issues/4342) reports exactly
this pairing failing: *"zooming the camera doesnt update the subViewPort + mouse position"*.

**What it does not say** — whether input forwarding accounts for the canvas transform at all. That is
the single fact the whole input chart rests on, and it decides between two very different
implementations.

**Why it blocks** — two defensible choices differ in observable behaviour (every click in every
screen lands in the wrong place, or does not), and it is expensive to reverse: the picture's node
type is the root of chart B and everything in chart I hangs off it. It meets the CONTRADICTION test
— the design asserts something the engine documentation argues against.

**Options I can see** — **(a)** prove it first — a throwaway scene with a container under a zooming `Camera2D` and a `Button` inside, clicked at three zoom levels; if clicks land nothing changes and this closes with evidence · **(b)** display each picture as a `Sprite2D` carrying a `ViewportTexture`, the documented way to put a viewport in world space, and route input with `SubViewport.push_input()` plus `make_input_local()` — more code, no fight with the class's intent · **(c)** keep the container and never scale it: the focused picture always draws at 1:1 and wall view is rendered from the frozen textures rather than by shrinking live containers · *my recommendation* (a)

**Blast radius** — design nodes B5, I1, I2, I3, H3, H5; every chart-I node; the whole of §12–§16.

**Meanwhile** — parked: the input mechanism and anything that depends on the picture's node type.
Continued on: layout, pause, transitions, persistence, unlocks, audio, the tool.
