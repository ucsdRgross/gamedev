# GAP-007 — R6's "exactly one push_error" cannot be observed, and satisfying R6 at all widens a global error blind spot
status: resolved
outcome: answered
raised: 2026-08-15, during execution plan step S7 (`ProfileManager`)

## Owner's answer — option (b)

**`_scan_engine_errors()` counts occurrences.** An allow-listed line is permitted *up to an expected
number*; a further occurrence still fails the run. This upgrades every `ENGINE_ERROR_ALLOW` entry
from "ignore this text forever" to "expect exactly N of this text", which is what makes R6 mean what
`TEST_PLAN.md` says it means and closes the blind spot on `user://profile.tres`.

⚠ **Shared harness work — all 33 suites depend on `_scan_engine_errors()`.** Every existing allow
entry needs its expected count established from a green run, not guessed; an entry whose real count
is 2 and whose declared count is 1 turns the whole suite red. Land it, then re-run the full suite and
confirm the suite count and failure set are unchanged before believing it.

This does not retroactively change S7, which is committed and green. R6 gains the count assertion it
was always specified to have.
design: TEST_PLAN.md §3 row R6; START_HERE "no silent failures"
severity: GAP

**What the design says** — `TEST_PLAN.md` §3, R6: *"a corrupt profile file degrades to defaults |
write garbage to the path → assert defaults and **exactly one** `push_error`"*. Its own footnote
makes the intent explicit: *"this repo's coding rules forbid silent failure paths, and a persistence
layer without a corruption test is one."*

**What the ANSWER says** — R6 is not from the questionnaire; `TEST_PLAN.md` §3 introduces it on the
repo's no-silent-failures rule. So there is no answer note to consult, and nothing that settles how
the count is to be observed.

**What it does not say** — **how "exactly one" is to be asserted, given a harness that cannot count
`push_error`.** Verified independently against the live harness, not assumed:

- GDScript exposes no hook over `push_error`, so a test cannot observe invocations at runtime.
- The harness's only error facility is `ENGINE_ERROR_ALLOW`, a single const substring-matched once
  by `_scan_engine_errors()` over the whole-run log. It distinguishes allow-listed from
  not-allow-listed; **it never counts occurrences**, so it cannot tell one from three.
- There is no per-suite or per-test allow-list in `TestSuite` / `test_base.gd`.

As shipped, R6 asserts that defaults load, and "exactly one" rests on `profile_manager.gd` having a
single `push_error` call site. That is a code-shape argument, not an assertion — it holds until
someone adds a second call site, which is precisely the regression R6 was written to catch.

⚠ **The collateral is the sharper half.** A genuinely corrupt file makes Godot's own `ResourceLoader`
emit three native errors that carry no distinctive prefix, so the only way to keep the suite green is
a **global** allow entry for `user://profile.tres`. Every suite in the run now silently tolerates any
engine error naming that path. **The test written to prove there is no silent failure path created
one**, and it will not be visible when it matters — S7's own `ProfileManager`, and later S30/S38
unlock work, all load that file.

**Why it blocks** — triage test (2): the choices differ in observable behaviour — under (a) a second
`push_error` or a real load failure on that path goes unreported forever; under (b) it fails the run.
It is not a local judgement call either, because the fix touches shared test infrastructure that
every suite depends on, which is beyond any single step's scope. It does **not** block S7 itself:
S7's done-when ("`TestWallProfile` is green; the autoload registers after `SettingsManager`") is met,
and the other five rows R1–R5 are unaffected.

**Options I can see** — **(a)** accept as shipped — defaults asserted, "exactly one" resting on the
single call site, the global allow entry retained; costs nothing now and leaves both an unenforced
assertion and a permanent blind spot on that path · **(b)** make `_scan_engine_errors()` count
occurrences, so an allow-listed line is permitted *up to an expected number* and a fourth occurrence
still fails the run — this is the only option that makes R6 mean what it says, and it upgrades every
existing allow entry from "ignore" to "expect exactly N"; it changes shared harness code that all 33
suites depend on · **(c)** withdraw the "exactly one" half of R6, keeping only "degrades to
defaults", and record that the repo's no-silent-failures rule is enforced here by code review rather
than by test — honest, cheap, and strictly weaker than what `TEST_PLAN.md` asked for ·
*my recommendation* **(b)**, because R6's stated purpose is defending against silent failure and (a)
and (c) both leave that undefended; but it is harness work and therefore an owner call on scope

**Blast radius** — `TEST_PLAN.md` R6; `Tests/all_tests.gd`'s `ENGINE_ERROR_ALLOW` and
`_scan_engine_errors()`, shared by all 33 suites; `Scripts/profile_manager.gd`'s load path. Any
future step loading `user://profile.tres` — S30, S38 — inherits the blind spot.

**Meanwhile** — parked: R6's exactness and the allow-list widening. Continued on: everything else.
S7 is complete and committed; R1–R5 are unaffected and green.
