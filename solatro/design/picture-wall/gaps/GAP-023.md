# GAP-023 — Info mode is entered by CLICK, and suppresses game actions

status: resolved
outcome: answered — click to inspect; no game action while Info mode is on
raised: owner playtest through `Tools/wall_editor.tscn`
design: `Q132`=a; `Q133`=b; `Q134`=c; chart J7, J8
severity: GAP

## OWNER ANSWER

**A click describes a card; hover does nothing.** Hovering is not enough because the pointer has to
leave the card to reach the info card and read or scroll it. **While Info mode is on, that click
performs NO game action** — the card is not picked up.

Controller scrolling of a long card is a separate input question and is not answered here.

## The question

`Q132`=a and chart J7 say screens publish hoverables and the card follows the pointer. Nothing in
the design covers a click, because nobody had used it yet.

⚠ **The first answer given rested on a wrong premise and was withdrawn.** It was: "inspects AND
performs the normal action, since a click without a drag is a pick-up-and-drop-in-place". **There is
no drag path in this game** — no `InputEventMouseMotion` handling in `play_area.gd`,
`card_visual.gd` or `game_view.gd`. A left click GRABS and HOLDS (`data_selected` →
`grab_cards()`); only right-click or `ui_cancel` releases it. So "also perform the normal action"
would have picked the card up on every inspection.

## What changed

`PlayArea` gained `info_requested(entry: InfoEntry)`. Both selection sites — the left click and
`ui_accept` — publish that entry INSTEAD of `data_selected` while Info mode is on. `GameView` relays
it and `Main` puts it on the wall's one card.

This also lands the other half of `Q134`=c / J8, which `S29` left undone: the board's own in-screen
inspector (`PlayArea._show_focus_info`) stays hidden in Info mode, so one card describes one thing.
`S29` migrated `map_hover_panel.gd` only — its done-when named the map and never the board.

## Follow-up answers (same playtest round)

**`wall_screen_popups` — whether a screen's own description exists outside Info mode.**
- `true` (default): the popup behaves as it always has when Info mode is off, and MIGRATES to the
  info card when Info mode is on.
- `false`: no popup at all; a description is only ever visible in Info mode.

Either way the popup NEVER shows while Info mode is on — that gate is separate and always wins.

**Controller scroll: the stick that has no d-pad beside it.** Normal movement is the side where the
stick and d-pad sit together, so the other stick is free for scrolling a long info card. NOT bound
yet — it needs an InputMap action and a real pad to verify.

## Room this leaves (owner note, not yet a decision)

The two surfaces can carry DIFFERENT text: the overlaid popup a short summary, the info card a much
deeper explanation. Nothing implements that split — both read `ControlCard.describe_card()` today,
which is deliberate (one string, no drift). Splitting them means a second authored description per
card and is its own question.

## The tool was not listening

`Main` connects `GameView.info_requested` and `Map.info_hovered`; `Tools/wall_editor.tscn` hosts the
same screens and connected NEITHER, so a card clicked in the preview raised an entry into the void
and the info card never changed. `_listen_for_info()` now connects either signal by NAME on any
hosted screen, so a third screen needs no change there.

## The visual in the card is a REAL node, made inert

An entry's visual is a real preview `ControlCard` with a live `CardVisual` (the float is its idle
animation), or a `TextureRect` mirroring a picture's own `SubViewport`. Real, because a stand-in
would show something the game does not.

⚠ Real also means it arrives INTERACTIVE: `ControlCard._ready()` sets `focus_mode = FOCUS_ALL`, so
it is a focus stop controller navigation can land on, and any `Control` defaults to
`MOUSE_FILTER_STOP`, so it would swallow clicks aimed behind the card. `InfoCard._make_inert()`
strips both recursively as the card takes ownership — one place, so a future `get_info()` cannot
forget. What survives is drawing and idle animation.

It cannot mutate what it shows: `CardVisual` never writes to its `CardData` (it reads
`CardEnvironment` for timing and nothing else), and no callback is wired — `CardsViewer.populate()`
connects `mouse_entered`/`focus_entered` only when given an `on_inspect`, and none is passed.

## Round 5 — the card is remembered PER SCREEN, and two sizing bugs behind it

**Each picture keeps the card it was showing.** Leaving a screen no longer resets it; coming back
returns to what you were reading. `InfoCard.detach_entry()` hands the entry back with its visual
DETACHED rather than freed, and the wall's owner stashes it per picture.
⚠ The stashed visual is then a Node outside the tree that nothing else collects — the owner frees
whatever it replaces and everything it holds on teardown. LEAK CANARY passes.

**The compressed first card, one letter per row.** `_visual_size()` took
`get_combined_minimum_size().max(size)`. A Control's `size` before its first layout pass is
whatever it happens to hold — for a fresh `ControlCard`, wider than the whole card — so
`text_width` hit its 1px floor. Minimum size only now, plus a hard ceiling
(`_VISUAL_MAX_WIDTH_SHARE`) so the text always keeps half the card whatever a visual asks for.

**The extreme zoom-out on the game view was the SAME bug.** One letter per row made the card
max-height tall, the info pose reserves the card's height, so the camera pulled back to clear a
card that was only that tall because its text had collapsed. Fixing the width fixed the zoom; it
was never a second defect.
