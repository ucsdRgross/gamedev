# GAP-015 — L3's "authored default background image" has no field to live in
status: open
raised: 2026-08-17, during execution plan step S31 (game as a picture)
design: DESIGN.md version 5, node L3; `Q191` note
severity: GAP

**What the design says** — `L3`: *"When there is no `GameView` the picture shows an authored default
background image, which `GameView` may update. Q191 note"* (`DESIGN.md:774`). `L2` requires
`GameView` to be built fresh per show and freed after, so the no-GameView state is the **normal**
resting state of the board picture, not an edge case.

**What the ANSWER says** — the `Q191` note establishes that the picture is never empty. It does not
name the image, its home, or who authors it.

**What it does not say** — **where the image lives.** `PictureEntry` (§1.1) has `scene` and
`frame_texture` and no background field; `WallLayout` (§1.2) has none either. So an authored
per-picture background has no home, exactly as `QR4`=(b)'s frame colour had none in **GAP-013**.

**Why it blocks** — triage test (2): adding a field to `PictureEntry` is a resource-format change
and `NAMES.md` fixes the identifier set, so inventing one is precisely the "two sessions invent two
names" failure that registry exists to prevent. It is also an art-direction call about what the
board looks like when no show is running.

**It does NOT block the `main.gd` wire-up.** The board picture can render nothing until this is
answered; the consequence is a blank picture at rest, which is cosmetic and visible only where a
`GameView` is absent. Treating it as a blocker would strand Phase 7's actual integration behind a
placeholder image.

**Options I can see** — **(a)** a `background_texture : Texture2D` field on `PictureEntry`,
defaulting to `null` — symmetrical with the existing `frame_texture`, per-picture, authored in the
S34 tool like everything else; it grows the resource format, though nothing is authored against it
yet so the cost is lowest now · **(b)** one shared default on `WallLayout`, since only the board is
known to need it — fewer fields, but a second picture wanting its own background forces the change
to (a) later · **(c)** no field: the picture renders the wall surface through, so an absent
`GameView` reads as an empty frame — cheapest, and withdraws `L3`, which was answered deliberately ·
*my recommendation* **(a)**, mirroring `frame_texture`, which is the same kind of per-picture
authored art and already sets the precedent

**Blast radius** — `PictureEntry`'s field list in `PLAN.md` §1.1 and `NAMES.md`; S34's tool, which
must expose *"every `PictureEntry` field per picture"*; the board picture's resting appearance. No
shipped code depends on it, and no layout is authored yet, so answering it now is free and answering
it after `layout_default.tres` exists is not.

**Meanwhile** — parked: the board's resting background only. Continued on: the `main.gd` wire-up,
which renders blank there in the interim, and everything else in Phase 7.
