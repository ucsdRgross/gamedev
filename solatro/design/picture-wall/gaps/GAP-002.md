# GAP-002 — the engine already has the wall-view resolution feature
status: resolved
outcome: answered
raised: 2026-08-15, during the post-chart engine verification pass
design: DESIGN.md version 3, nodes E5, B5
severity: GAP
resolution: |
  ⚠ **Answered (a) in chat, and GAP-001 was answered (b) in the same message. Those two cannot both
  stand:** `stretch_shrink` is a property of `SubViewportContainer`, and GAP-001 (b) removes that
  node from the design. This file predicted the collision — *"my recommendation (a), falling back to
  (c) only if GAP-001 resolves to the `Sprite2D` route"* — so the fallback is what fires.

  **Carried over as the principle, not the property.** What (a) chose was "one engine property, not
  a subsystem", and on the `Sprite2D` route that is `SubViewport.size` written directly: shrink the
  viewport, leave the sprite's scale alone, and the picture renders at fewer pixels while occupying
  the same wall space. It is the same one-line idea `stretch_shrink` packaged, and it is strictly
  more flexible — `stretch_shrink` is an integer divisor, `SubViewport.size` is any size, which
  `Q87`=(b)'s derive-from-on-screen-pixel-size rule wanted anyway.

  Option (c) — a hand-rolled resolution manager — is explicitly NOT taken. There is no manager: one
  property, written when the picture's on-screen size changes.

  ⚠ **If that is not what you meant, this is the line to correct.** Design v5 charts it as E5.


**What the design says** — `Q86`=(a) plus `Q87`=(b), charted as **E5**: *"NEW Wall-view resolution is
separate and derived from the picture's on-screen pixel size at wall-view zoom."* The word NEW is the
problem.

**What the ANSWER says** — `Q86`=(a) *"yes — a wall-view resolution per picture, distinct from its
focused resolution"*, `Q87`=(b) *"derived from the picture's on-screen pixel size at wall-view zoom"*.
Both answered without a note. The intent is clear and correct; what is wrong is my charting it as
something to build.

**What the docs say** —
[SubViewportContainer](https://docs.godotengine.org/en/stable/classes/class_subviewportcontainer.html)
already ships `stretch_shrink`:

> *"Divides the sub-viewport's rendering resolution by this factor while maintaining visual scale."*

That is the feature, verbatim, with `stretch = true` sizing the viewport to the control. Your own
`Q17` note reached for the same idea — *"possibly a for performance to reduce frozen picture
resolution kind of like mipmap"* — and the engine has it.

**What it does not say** — whether a per-picture integer shrink factor is enough, or whether the
derived-from-pixel-size rule in `Q87`=(b) needs finer granularity than integer division gives.

**Why it blocks** — it does not block much, but it is a contract question: E5 tells an implementer to
build a resolution manager, and the honest instruction is "set one integer property". Left as-is,
the plan specifies an invention. It is also entangled with GAP-001: `stretch_shrink` only exists on
`SubViewportContainer`, so choosing GAP-001 (b) loses it and the manual version comes back.

**Options I can see** — **(a)** use `stretch_shrink`, set per picture from its on-screen size and quantised to integers — the engine's own feature, one property instead of a subsystem · **(b)** use `stretch_shrink` for the coarse steps plus `SubViewport.size_2d_override` where an integer step is too coarse · **(c)** keep the hand-rolled resolution manager, because it survives GAP-001 either way · *my recommendation* (a), falling back to (c) only if GAP-001 resolves to the `Sprite2D` route

**Blast radius** — design nodes E5, B5, H1; plan steps that build render gating.

**Meanwhile** — parked: the wall-view resolution mechanism. Continued on: everything else in chart E,
which is unaffected — freezing via `UPDATE_DISABLED` is correct regardless.
