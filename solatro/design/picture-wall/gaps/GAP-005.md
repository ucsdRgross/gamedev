# GAP-005 — the OS reduced-motion preference IS available, and the question said it was not
status: resolved
outcome: answered
raised: 2026-08-15, during the post-chart engine verification pass
design: DESIGN.md version 3, nodes K8
severity: CONTRADICTION
resolution: |
  Answered (a) in chat: `wall_reduced_motion` takes its FIRST-LAUNCH default from
  `DisplayServer.accessibility_should_reduce_animation()`, and becomes an ordinary stored setting the
  moment the player touches it. The OS is a default, never an override — a player who turns wall
  motion back on keeps it on regardless of what the OS says afterwards.

  This supersedes `Q174`=(a), which was answered against a note of mine that wrongly said the query
  was unavailable.

  ⚠ Carried forward UNVERIFIED: a report exists that the sibling
  `accessibility_should_reduce_transparency()` did not track the Windows setting in testing. The
  first-launch read must be checked against the actual OS toggle before it is trusted, and it needs
  a defined behaviour when the query is unavailable or returns nothing — default OFF, matching
  `Q174`'s original answer.


**What the design says** — `Q174`=(a), charted as **K8**: reduced motion is *"off by default"*. The
question's own note told you: *"Godot does not expose an OS reduced-motion query on every platform;
(b) may reduce to (a) in practice."*

**What the ANSWER says** — `Q174`=(a) *"no"*, no note. But (a) was chosen against option (b) —
*"it follows the OS reduced-motion preference where the platform exposes one"* — that I had
described as probably unavailable. **The note was wrong, so the choice was made on a false premise.**

**What the docs say** — `DisplayServer.accessibility_should_reduce_animation()` exists, alongside
`accessibility_should_increase_contrast()` and `accessibility_should_reduce_transparency()`. It
arrived with the AccessKit integration in **Godot 4.5** ([release notes](https://godotengine.org/releases/4.5/)),
and this project runs **4.7** (`project.godot`: `config/features=PackedStringArray("4.7", …)`). So
the query is available right now, on this version, with no addon.

⚠ One caveat worth carrying: a report exists that `accessibility_should_reduce_transparency()` did
not track the Windows setting in testing while the theme-change callback did fire. The sibling
method may be equally patchy on Windows, so ⚠ **UNVERIFIED — check it against the actual OS toggle
before relying on it** (repo rule 4).

**What it does not say** — whether following the OS preference should *set* the flag's default or
merely *offer* it, and what happens if the player then overrides it by hand.

**Why it blocks** — it is an accessibility default, which is exactly the class of decision the
protocol reserves for the owner, and it is one the design talked you out of with a false fact. It
also fixes a literal in the tunables table.

**Options I can see** — **(a)** `wall_reduced_motion` defaults to whatever `accessibility_should_reduce_animation()` returns on first launch, then becomes a plain stored setting the moment the player touches it — the OS is a default, never an override · **(b)** follow the OS preference live on every launch, with no player override · **(c)** leave it as you answered, off by default and player-set only, now knowing the query exists and choosing not to use it · *my recommendation* (a)

**Blast radius** — design node K8, K9; the `wall_reduced_motion` row in the tunables table.

**Meanwhile** — parked: the reduced-motion default. Continued on: what reduced motion *does*, which
`Q172`=(a) and `Q173`=(a) settle and this does not touch.
