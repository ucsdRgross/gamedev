# GAP-013 — QR4=b's frame "colour" parameter has no fixed home

status: resolved
outcome: answered
raised: 2026-08-16, during execution plan step S24 (frame art parameters)

## Overseer note — this gap owns EVERY unhomed frame/shadow appearance value, not just colour

Three literals are the same class of decision and should be answered together, so the frame's look
has one home rather than three:

- **frame colour** — the gap as filed.
- **shadow opacity** — `Color(0, 0, 0, 0.35)`, a `.gd` literal since S10. A visible design choice,
  so §1.8 makes it a defect exactly as `_OVERFILL_MARGIN` was (GAP-011, answered: make it a knob).
- **the frame bevel's two `Color()` literals** — added by S24's generated placeholder texture.

⚠ **The palette drift-scan count is the ledger for this**: 18 → 19 (wall colour, S9) → 20 (shadow
tint, S10) → **22** (frame bevel, S24). Each rise is a hardcoded colour no palette role owns.
Warnings never fail the suite, so this can creep indefinitely — **a rise without a matching gap
entry is the signal that it is creeping.** Whatever answers this must say whether these live on
`PictureEntry`, on `PlayerSettings`, or as palette roles.
design: DESIGN.md version 5+, node B6, gate QR4=b
severity: GAP

## OWNER ANSWER — option (a), plus a ruling on the two values this gap was widened to cover

**Frame colour: `frame_colour : Color` on `PictureEntry`, per-picture**, defaulting to the current
neutral placeholder tone. This is this file's own option (a) — it mirrors how `frame_px` (the other
half of `B6`'s "size and colour") already works per-picture, and it is consistent with **GAP-015**'s
ruling that `PictureEntry` is extensible.

⚠ **Correction:** the overseer's summary to the owner mislabelled this gap's option (a) as
"PlayerSettings knobs". The owner answered "take all recommendations", and this file's recommendation
is per-picture `frame_colour`. That is what is recorded here.

**The two values this gap was widened to cover are wall-wide, not per-picture**, so they do NOT go on
`PictureEntry`:

- **shadow opacity** (`Color(0,0,0,0.35)`) → a `PlayerSettings` knob, `wall_shadow_opacity`,
  alongside `wall_light_offset`, which S25 already established as the one-authored-value-for-everyone
  precedent for shadows.
- **the bevel's two `Color()` literals** → they belong to the generated placeholder texture, which
  `QR4`=(b) explicitly defers to a later art pass. They stay as they are **only until that art pass**,
  and the palette drift count (currently 22) is the ledger that keeps them visible.

Expose `frame_colour` per picture and `wall_shadow_opacity` in S34's tool, and add both rows to
`DESIGN.md` §5 / §1.1 as appropriate.

**What the design says** — `B6`: *"Frame — one shared style parameterised by size and colour
QR4=b."* `QR4`=b's own text: *"one shared frame style parameterised by size and colour, the shader
and art pass deferred — next: the parameters of that one style only."*

**What the ANSWER says** — the frame is ONE shared style (one texture/pattern, no per-frame
shaders or unique art, PLAN.md §4 anti-scope item 7), and that one style takes two parameters:
size and colour. "Size" is already fixed elsewhere — `PictureEntry.frame_px` (per-picture,
per-side thickness in wall units, `Q36`/`Q37`) already IS the size parameter, transcribed
verbatim in `PLAN.md` §1.1.

**What it does not say** — **where "colour" lives, or whether it varies per picture or is one
value for the whole wall.** `PLAN.md` §1.1's `PictureEntry` field list is fixed and exhaustive (10
fields, transcribed exactly, `ring` deleted by GAP-009) and contains no colour field. `NAMES.md`
fixes no such field either. Two readings are both consistent with B6's text: (1) colour is
authored PER PICTURE, alongside `frame_px`, so different pictures can have visibly different frame
tints while sharing one texture — the reading that mirrors how "size" already works; (2) colour is
ONE value for the whole wall (closer to how `wall_light_offset`, S25's own new knob, is "one
authored position" for everyone) — the reading that keeps `PictureEntry` unchanged.

**Why it blocks** — triage test (2): §1.1's field list is a fixed contract (`PLAN.md`'s own gap
protocol rule — a step may not add a field the plan does not name), so adding
`PictureEntry.frame_colour` on my own authority would be a decision this run's rules explicitly
reserve for the owner/coordinator, not the implementer.

**What shipped instead, and it is NOT blocked by this gap** — S24's other four parameters (`Q36`
thickness-as-fraction, `Q37` per-side authoring, `Q38` frame-outside-the-rect, `Q39` no mat, `Q41`
frameless-still-shadowed) were all already correctly built by earlier steps (S3/S4/S8/S10) and
needed no change. The one shared `NinePatchRect` texture and its patch-margin wiring (genuine
nine-slice behaviour, corners fixed, edges stretched) are built and use ONE fixed neutral tone
baked into the generated placeholder texture itself — not a knob, the same "diagnostic/placeholder
art generation is not an author-tunable number" category `_swatch_texture()` and `NATIVE_SIZE`
already sit in elsewhere in `Tests/Visual`. TEST_PLAN §10 item 2's by-eye check (does the corner
art hold at the largest and smallest picture) is answerable without per-picture colour at all.

**Options I can see** — **(a)** `frame_colour: Color` on `PictureEntry`, per-picture, defaulting to
the current neutral placeholder tone · **(b)** `wall_frame_colour: Color` on `PlayerSettings`, one
value for the whole wall · **(c)** leave it unparameterised for v1 and record that "colour" in B6
is currently satisfied only by the placeholder texture's own baked-in tone — cheapest, defensible
only if per-picture/per-wall colour variation is never going to be argued with · *my
recommendation* **(a)**, because it mirrors how `frame_px` (size) already works and S34's tool
(PLAN §2, done-when: "no knob above requires editing a `.tres` or a `.gd` by hand") will want a
per-picture colour field to expose regardless of which reading is chosen.

**Blast radius** — `Scripts/Wall/picture_entry.gd` (a new field, if (a)); `Scripts/player_settings.gd`
(a new export, if (b)); `UI/Wall/wall_picture.gd`'s `build()` (reads whichever knob wins);
`PLAN.md` §1.1's fixed field list, which would need the owner's own amendment to stay authoritative.

**Meanwhile** — parked: per-picture or per-wall frame colour variation. Continued on: everything
else S24 owes (nine-slice geometry, patch margins, shared texture) and all of S25.
