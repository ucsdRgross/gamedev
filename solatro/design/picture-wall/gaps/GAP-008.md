# GAP-008 — four values have two homes, and the packer can only read one of them
status: resolved
outcome: answered
raised: 2026-08-15, during execution plan step S8 (the `PlayerSettings` block)

## Owner's answer — option (a)

**`WallLayout` wins. The four `PlayerSettings` rows are struck**: `wall_gap`, `wall_view_margin`,
`wall_ellipse_aspect_min`, `wall_ellipse_aspect_max`. The values live only on `WallLayout` as
`gap_px`, `view_margin`, `ellipse_aspect_min`, `ellipse_aspect_max`.

`WallPacker` stays pure and headless-testable per §1.3, S34 edits them as layout fields per its own
`WallLayout` list, and no signature changes and no test is withdrawn.

⚠ **`DESIGN.md` §5's table still lists all four and must be amended at source** — until it is, S8's
done-when ("every row of §5") and this resolution disagree, and the next reader will re-add them.
The `PlayerSettings` "Picture wall" group is therefore **18** §5 knobs, not 22.
design: DESIGN.md version 5, §5 tunables; PLAN.md §1.2, §1.3, §1.8, S34
severity: CONTRADICTION

**What the design says** — `DESIGN.md` §5 lists `wall_gap` (24), `wall_view_margin` (0.06) and
`wall_ellipse_aspect_min` / `_max` (1.2 / 2.6) as `PlayerSettings` knobs. `PLAN.md` §1.2 puts the
same four values on `WallLayout` as `gap_px` (24.0), `view_margin` (0.06) and `ellipse_aspect_min` /
`_max` (1.2 / 2.6). **Same meanings, same defaults, different names, two homes.**

**What the ANSWER says** — the questions behind them fix the *values*, never the *home*: `Q14`=(a)
one uniform gap for the whole wall (`DESIGN.md:903`), `Q10`=(c) the ellipse aspect clamped to an
authored min/max (`DESIGN.md:899`), `Q5` the wall-view margin (`DESIGN.md:891`). None says whether
"authored" means the layout resource or the settings file, so this is not rule 4 — there is no
single source answer both documents are restating.

**What it does not say** — **which home is authoritative.** It matters because the two are not
interchangeable: `WallPacker.pack(layout, unlocked, window_aspect)` is specified as a pure function
with *"no randomness, no node access, no engine singletons — so it is testable headless"*
(`PLAN.md` §1.3). It therefore **cannot** read `SettingsManager.settings`. Every packing rule in
§1.3 names the layout fields — `layout.ellipse_aspect_min`, `layout.gap_px`. So as specified, the
four `PlayerSettings` copies have **no reader at all**.

`PLAN.md` §1.8 states the principle as an exclusive choice — every arguable value is *"either a
`PlayerSettings` knob (`DESIGN.md` §5) **or** a field on `WallLayout` / `PictureEntry`"* — and these
four are both. S34's own requirements already split them the same way §1.2 does: its `WallLayout`
list names `gap_px`, `home_id`, the ellipse clamps and `view_margin`, while its `PlayerSettings`
list names the transition clock, the phase shares, the easings, `wall_frame_reveal_margin`,
`wall_view_min_texture_px`, the touch trio and `wall_pinch_threshold_px` — **and not** `wall_gap`,
`wall_view_margin` or the ellipse clamps. Two parts of the plan already disagree about where these
live.

**Why it blocks** — triage test (3), the design contradicting itself, and the failure mode is
silent. A knob that exists in the settings UI and in the S34 tool but has no reader will be changed
by someone expecting the wall to re-pack, and **nothing will happen** — with no error, because
nothing is wrong from the engine's point of view. That is precisely the "a control that silently
does nothing is the defect" lesson `TEST_PLAN.md` F8 already encodes for the Back button.

It does **not** block S8, whose done-when is mechanical: every §5 row exists as an export. Those four
are being implemented literally as written, unresolved and unwired, pending this answer.

**Options I can see** — **(a)** `WallLayout` wins and the four §5 rows are struck — the packer stays
pure and headless-testable exactly as §1.3 requires, S34 edits them as layout fields per its own
`WallLayout` list, and the values ship with the layout resource rather than with the player's
settings; costs the ability to tune them per-player · **(b)** `PlayerSettings` wins and the four
`WallLayout` fields are struck — the values become player-tunable and live-editable through the
settings screen, but `pack()` must then take them as explicit arguments to stay pure, changing the
§1.3 signature and every `TestWallPacker` fixture · **(c)** both stay, with `WallLayout` seeded from
`PlayerSettings` at construction — nothing is deleted and both documents stay literally true, at the
cost of two names for one value and a copy that goes stale the moment either side changes ·
*my recommendation* **(a)**, because §1.3's purity constraint and S34's own field list both already
assume it, and it is the only option that changes no signature and withdraws no test

**Blast radius** — `PLAN.md` §1.2 and §5's tunables table; steps S4, S34, S36; `TestWallPacker`
fixtures P2, P6, P7 which set these values on the layout. No runtime code depends on the answer yet,
which is why answering it now is cheap and answering it after S34 is not.
