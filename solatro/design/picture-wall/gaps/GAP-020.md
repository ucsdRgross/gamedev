# GAP-020 — what does Back do while the wall view is showing?

status: resolved
outcome: answered — option (a)
raised: fixing the wall-view Back defect an adversarial review found
design: `Q65`=a; `Q66`=b; §1.4 (`FocusStack`)
severity: GAP

## OWNER ANSWER — option (a)

**Back returns to the picture you just left.** Already implemented in `Main._on_back_pressed()`'s
wall-view branch. The cost this option carries is now paid too: `WallOverlay.refresh()` takes an
`in_wall_view` flag, so the Back BUTTON is enabled exactly when the Back KEY does something. Without
it the button was greyed out in wall view on a one-entry stack while Escape still worked — the
divergence `Main._ready()` explicitly promises cannot happen.

## The question

`FocusStack._back`'s last element IS the current picture, and wall view is never an entry
(`Q66`=b). So while the wall view is showing, `Main._current_focus` is `&""` but the stack still
sits on the picture the player just left. `Q65`=a describes Back as retracing "one step at a time"
and bottoming out AT wall view — it does not say what Back does once you are already there.

- **(a) Back returns to the picture you just left** (the stack's own top, no cursor movement).
  Back reads as "undo my Wall press", and the overlay's Back button — which `can_back()` already
  enables in wall view — does something when pressed. **This is what is implemented now.**
- **(b) Back is inert in wall view.** Wall view is where Back terminates, so it is the bottom and
  there is nothing below it. Then the overlay's Back button must also be DISABLED there, which
  `overlay.refresh()` cannot currently express — it keys on `can_back()` alone and knows nothing
  about wall view.

## Why it is a gap and not a judgement call

Both are coherent readings of `Q65`=a, and they differ on a control the player presses constantly.
(b) additionally needs the overlay to learn about wall view, so it is not a pure swap.

## What was NOT in dispute, and is already fixed

The shipped behaviour was neither option: it called `back()`, which stepped PAST the picture just
left and pushed it onto the FORWARD list. Measured — leave `map`, press Back once, land on
`start_menu`, and `map` is now ahead of you having never been revisited. A single, unraced press.
No reading of `Q65`/`Q66` endorses that, so it is a defect either way.

## An edge (a) leaves slightly ragged

With exactly ONE entry in the stack, `can_back()` is false (it requires two) so the overlay's Back
button is disabled — while `current()` is non-empty, so a press *would* have somewhere to go. Wall
view reached from the very first picture is the only way to hit it. Choosing (a) properly means
`overlay.refresh()` learning whether the wall is showing; choosing (b) means the same call learning
it for the opposite reason.

## What is reversible about it

Cheaply: one branch in `Main._on_back_pressed()` plus `FocusStack.current()`, which has no other
caller.
