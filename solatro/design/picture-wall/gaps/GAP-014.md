# GAP-014 — the opening reveal is "longer, slower" than an ordinary transition, with no number anywhere
status: open
raised: 2026-08-17, during execution plan step S30 (screens onto the wall)
design: DESIGN.md version 5, nodes M1, M2, M3; `Q61`=(a), `Q62`=(a)
severity: GAP

**What the design says** — `M2`: *"Choosing a save triggers a one-off **longer, slower** zoom-out to
wall view, distinct from an ordinary Wall press. Q61=a"* (`DESIGN.md:803`). `M3`: *"That reveal
happens on EVERY launch. Q62=a"* — so it is not a once-ever flourish, it is on the critical path of
every single boot.

**What the ANSWER says** — `Q61`=(a) fixes *that* the reveal is distinct and slower. `Q62`=(a) fixes
that it happens every launch. Neither says by how much.

**What it does not say** — **how long the reveal takes.** `DESIGN.md` §5 has no row for it. The
transition clock is `base_delay × wall_transition_delay`, which is by definition the *ordinary*
duration M2 says this must differ from. There is no multiplier, no separate delay, and no easing
selection for it.

⚠ **§1.8 forecloses the obvious workaround.** *"If you find yourself typing a literal into a `.gd`
file that is not in one of those three places, stop — that is a gap."* A reveal that is "1.8× the
normal transition" or "2.5 s" is exactly such a literal, and this run has already produced two of
them — `_OVERFILL_MARGIN` (GAP-011, answered: make it a knob) and the frame/shadow colours
(GAP-013). Typing a third would be the same mistake a third time.

**Why it blocks** — triage test (2): the choice is an owner call about feel, on an animation the
player sees on **every launch**, and different values are visibly different products. It is also the
first thing anyone sees, so it is the least appropriate number in the feature to guess at.

It blocks only the reveal's choreography in `Levels/main.gd`. The rest of S30 — reparenting live
screens, the initial layout, the cold-launch focus stack — is built and tested, and **S31 does not
depend on it at all**.

**What is NOT a gap, and was mistaken for one:** whether the reveal lands on wall view or
auto-focuses the destination picture. **M2 settles it** — *"a one-off longer, slower zoom-out **to
wall view**"*. It lands on wall view. `M4` (*"Wall view is hidden entirely while only one picture
exists"*, `Q19`=b) does not conflict: at the moment of the reveal, choosing a save has unlocked more
than one picture. No decision is outstanding there.

**Options I can see** — **(a)** a `PlayerSettings` multiplier, `wall_reveal_delay_scale`, applied to
the same `base_delay × wall_transition_delay` clock — one knob, tunes with everything else, and
S34's tool exposes it like every other wall number; the reveal stays locked to the ordinary
transition's feel and can only be scaled, not reshaped · **(b)** its own absolute duration knob plus
its own easing selection, independent of the transition clock — the reveal can be shaped as its own
piece of choreography, which is what "distinct from an ordinary Wall press" implies, at the cost of
two more knobs and a second code path · **(c)** reuse the ordinary transition unchanged and drop
"longer, slower" — cheapest, and withdraws `Q61`=(a), which was answered deliberately ·
*my recommendation* **(a)** — it satisfies M2's "distinct" with one number, keeps a single
transition implementation, and is trivially upgraded to (b) later if the feel needs reshaping

**Blast radius** — `Levels/main.gd`'s boot choreography; `DESIGN.md` §5's table; step S30; S34's
tool, which must expose whatever knob this adds. No shipped code depends on the answer yet, which is
why answering it now is cheap.

**Meanwhile** — parked: the reveal's choreography in `main.gd` only. Continued on: S31 and the rest
of Phase 7, none of which touch it.
