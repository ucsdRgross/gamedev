# GAP-011 — `BoardCoord` is a reference type, so a mechanical migration silently breaks every equality guard

status: resolved
outcome: answered
raised: 2026-08-27, during execution plan step S20b.2b (the coordinate migration)
design: grid-view DESIGN.md v2 chart `M1`, `M3`, `M8`; `Q24`=(a), `Q26`=(a), `Q27`=(a); PLAN.md S20b
severity: CONTRADICTION

## OWNER ANSWER — (a), on the recommendation

Owner, verbatim:

> *"i will take your reccomendations for the gaps, since i assume it is best options for migrating
> to the new plan setup."*

The rules this produces:

- **Option (a).** `BoardCoord` stays the one coordinate type, as `M1` asked. It gains value
  affordances: an `equals(other)` method, a `pack() -> Vector4i` for dictionary keys and `find`,
  and an `is_nowhere()` predicate. Every `==` guard and every `find` over coordinates moves to them.
- ⚠ **This lands as its OWN green step, BEFORE any `Vector3i` is swapped.** It is purely additive,
  so it is provable on its own; done afterwards it is unverifiable, because the swap it protects
  would already have happened.
- ⚠ **(a)'s known weakness must be gated, not just documented.** `equals` can be forgotten at a
  call site where `==` could not be, and a forgotten one compiles clean and fails silently. So this
  step also owes a **source-scanning gate** that fails on `==` / `!=` applied to a `BoardCoord`,
  built on the shape of `run_effect_api_boundary_gate()` in `Tests/Engine/test_grid_cards.gd`,
  including that gate's `scanned >= N` self-check. Without it, (a) is strictly worse than (b).
- The two "not there" conventions are unified on `NOWHERE` per `M3`/`Q26`=(a): `cell_type_coord`
  and `Board.locate_in_cell` stop returning `null`. `is_nowhere()` is what callers test, never
  `== BoardCoord.NOWHERE`, so a rebuilt sentinel compares equal to the singleton.

## What the design says

`M1` — *"slot_center_global takes a BoardCoord and nothing else - one coordinate type everywhere"*,
and `Q24`=(a) chose that with no second `Vector3i` form. `M8` says the call sites *"move; no shim is
left behind"*. `M3`/`Q26`=(a) say an off-board card reports `BoardCoord.NOWHERE`.

## What it does not say

**How a `BoardCoord` is COMPARED, hashed, or used as a dictionary key.** The design treats the
coordinate as if it were a value, because the thing it replaces is one. It is not.

## What the repo says - measured

- `Scripts/board_coord.gd:1-2` - `class_name BoardCoord` / `extends RefCounted`. The whole file is
  73 lines and defines **no equality, no hash, no pack, no `is_nowhere`** (verified: a grep for
  `_eq|equals|hash|_to_string|is_nowhere|pack` returns nothing).
- GDScript has no operator overloading, so `==` on a `RefCounted` is **identity**, and it cannot be
  made value equality on this type at all. `BoardCoord.new(0,1,2,3) == BoardCoord.new(0,1,2,3)` is
  **false**.
- ⚠ **The codebase already hit this and worked around it.** `Scripts/game_data.gd:241-243`, in a
  comment: *"Keyed on a value-type `Vector4i(grid,x,y,h)` rather than a `BoardCoord` instance, since
  BoardCoord is RefCounted and hashes by identity, not value."* The `Vector4i` key is used at
  `:289`, `:310` and `:573`.
- The product tree carries **148 `Vector3i` references across 29 files**, ~30 of which are
  `if v == Vector3i.MIN` guards. On a mechanical swap each becomes an identity test that is
  always-false, compiles clean, and fails silently at runtime.
- `Levels/game.gd:1211` - `row_slot_path_from` does `full.find(coord)`; `Array.find` on a
  `RefCounted` is identity-based, so it returns `-1` and the function **silently returns the whole
  row** (`:1212-1213`). Nothing crashes and no current test covers it.
- `UI/play_area.gd:34` keys `_row_open` on `Vector2i`, derived from a coordinate at `:872`.
- ⚠ `NOWHERE` is a shared singleton (`board_coord.gd:18-21`), so `coord == BoardCoord.NOWHERE`
  works **only** for code that returns that exact instance. A freshly built coord with the same four
  sentinel components is a different object. `Tests/Engine/test_grid_board.gd:131-132` asserts on the
  components, not on identity - the two conventions already disagree.
- Two "not there" conventions coexist: `grid_position_of` returns `NOWHERE`
  (`game_data.gd:296`) while `cell_type_coord` (`:270`) and `Board.locate_in_cell`
  (`board.gd:292`) return **null**.

## Why it matters

This is the difference between a migration that is verifiable and one that is not. A green suite
after the swap **proves nothing**, because the two suites that exercise this geometry
(`test_ui_props`, `test_visual_layers`) build legacy-zone boards the migrated code never reaches.
The failure mode is a prop quietly anchoring to the wrong slot, not a crash.

## Options I can see

- **(a)** Keep `BoardCoord` as the one type and give it value affordances - an `equals(other)`
  method, a `pack() -> Vector4i` for dictionary keys and `find`, and an `is_nowhere()` predicate -
  then rewrite every `==` guard and every `find` to use them · **(b)** Carry the coordinate as a
  **value type** `Vector4i(grid,x,y,h)` at every seam that needs equality, hashing, a dictionary key
  or `find`, keeping `BoardCoord` as the constructor and helper layer - this is what `game_data.gd`
  already chose for its own index, so it would make one existing workaround into the rule · **(c)**
  Convert `BoardCoord` from `RefCounted` to a plain `Vector4i` type alias plus static helpers,
  retiring the class entirely · *my recommendation* **(a)**, because `M1` asked for one coordinate
  type everywhere and (b) reintroduces two representations, which is the thing `M8` forbids - but
  (a) is strictly more edits than (b) and its `equals` can still be forgotten at a call site, where
  (b)'s `==` cannot

⚠ Whichever wins, **it must land BEFORE any `Vector3i` is swapped**, as its own green step. A
value-semantics change is additive and provable on its own; done afterwards it is unverifiable.

**Blast radius** - plan step `S20b.2b` (and therefore `S20b.3`, `S20b.4`); design nodes `M1`, `M3`,
