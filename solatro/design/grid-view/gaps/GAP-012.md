# GAP-012 — `M2`'s "pure arithmetic" cannot describe a grid cell, because a grid panel's origin is a layout result

status: open
outcome: unanswered
raised: 2026-08-27, during execution plan step S20b.2b (the coordinate migration)
design: grid-view DESIGN.md v2 chart `M1`, `M2`; `J6`; PLAN.md S20b
severity: CONTRADICTION

## What the design says

`M2` — *"it stays PURE ARITHMETIC: no control-rect reads, so geometry never depends on relayout
timing"*. The intent is stated in the code too (`UI/play_area.gd:341-346`) and it is a real
requirement: props anchor through this function **every frame**, and a rect read mid-relayout gives
a stale or zero rect.

## What it does not say

**Where a grid panel's origin comes from.** The zone version could be pure-ish because both zone
`HBox`es are direct children of one `VBox` at a known offset. Grid panels are not.

## What the repo says - measured

- `UI/play_area.gd:353-368` - the current `slot_center_global(v: Vector3i)` opens with
  `var origin := hbox.global_position` (`:355`). ⚠ **`M2` is therefore already false today.** The
  doc comment claiming otherwise is about `control_for_coord` and rect *sizes*, not the container
  origin. It is harmless today only because the offset happens to be stable.
- `UI/play_area.gd:648-649` - `_create_grid_panel` sets
  `panel.size_flags_vertical = Control.SIZE_SHRINK_END` and
  `panel.size_flags_horizontal = Control.SIZE_SHRINK_CENTER`, and the panels live inside an
  `HBoxContainer` (`:141`).
- So a panel's origin is **the container's layout result**: bottom-alignment against every other
  grid's current stack height, and horizontal centring against every other grid's current width. It
  is not derivable from `(grid, x, y, h)` by arithmetic without either reading the panel rect
  (violating `M2`) or reimplementing `HBoxContainer`'s alignment over every grid's live dimensions.
- ⚠ **GAP-010 already measured this failure mode once**, from the other direction:
  *"`slot_center_global` STOPS MIRRORING THE CONTAINER the moment the row is centred. Its formula
  starts at `hbox.global_position.x`; with `ALIGNMENT_CENTER` the children start at an offset inside
  the hbox, and the math and the controls disagree by half the slack (measured: 20 px)."* That is
  the same contradiction, and `SIZE_SHRINK_CENTER` reintroduces it per panel.
- Two further dependencies of this function have **no grid equivalent and are named nowhere in
  chart `M`**: `_row_open_offset` (`:367`) -> `_row_covers_anything` (`:101-107`), which reads the
  `upper_zone`/`lower_zone` arrays directly; and `PropLayer._row_bounds` (`:242`) ->
  `PlayArea.row_card_visuals` (`:375-377`), which is `upper_zone_right if v.x == 0 else
  lower_zone_right`.

## Why it matters

`M7` — props anchoring again — is the payoff of the whole step, and props re-anchor every frame. If
the anchor reads a container rect, a prop's position depends on relayout timing, which is exactly
what `M2` exists to prevent. If it does not, the arithmetic and the controls disagree and cards
draw off their cells - measured at 20 px once already.

## Options I can see

- **(a)** Position grid panels by ARITHMETIC rather than by container flags - give the
  `%GridContainer` fixed per-panel offsets computed from the grids' dimensions, so `M2` holds and
  the panel origin is derivable · **(b)** Let `slot_center_global` read the panel rect once per
  frame and cache it, formally retiring `M2` and accepting the relayout-timing dependency it
  warns about · **(c)** Keep container layout but have each panel PUBLISH its resolved origin on
  `resized`, so the function reads a cached value rather than a live rect - arithmetic downstream of
  one event, not of the tree · *my recommendation* **(c)**, because it keeps the every-frame path
  free of tree reads (the actual point of `M2`) without reimplementing a container Godot already
  ships - but it is a new invalidation path, and a missed `resized` shows up as cards drawing
  off their cells rather than as an error
