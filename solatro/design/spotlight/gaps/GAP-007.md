  - **Cascade** — a preset may carry `sections`, walked in order with the show pulsing once per

    chart E's travel needs. `S5` is the full act's shape and is where the missing travel is visible.
  - **Mocked solo activation trigger** — `"casual": true` drives chart T's momentary cue at

    cannot do this yet, and `slot_center_global` is pure uniform-pitch math that a per-row expansion
    breaks — which is exactly the problem plan step S17 (gutters and prop anchors) has to solve.
- ⚠ **ONE IMPLEMENTATION FINDING THAT OUTLIVES THIS GAP: everything renders into a `SubViewport`.**
  `light.gdshader` is screen-space and resolves `SCREEN_UV` against whatever viewport it draws into,
  while a card's `global_position` is only "the screen pixel" because the game has one canvas layer
  and no camera offset. **The editor's own 2D view has a pan and a zoom**, so a light layer parented
  straight into an edited scene slides against its cards the moment anyone scrolls. The `SubViewport`
  restores the game's assumption exactly — and its size IS the brief's *"dummy screen size to dictate
  beam origins"* (`Q177`=a), for free rather than as a separate control.
- ⚠ **`LightLayer` GAINED `@tool`, AND ITS `_ready()` DELIBERATELY STILL DOES NOTHING IN THE EDITOR.**

  it in. The build moved to a public `ensure_built()` the tool calls on its own instance; nothing
  owned by an edited scene is touched, and `game_view.tscn`'s editor appearance is unchanged.

## The contradiction, measured rather than argued

`Q176`=(a): *"both — `@tool` for live knob dragging, runnable so an agent can screenshot it without
opening the editor"*.
`Q174`=(a) and `Q175`=(a): a **real** `PlayArea`, **real** `CardVisual`s and a **real headless
`Game`** with a fixed deck — *"the only way the firing order and the cascade are the real ones"*.

Verified on the shipped tree, 2026-08-04:

```
$ head -1 Levels/game.gd Levels/game_view.gd UI/play_area.gd UI/light_layer.gd UI/spotlight_director.gd
extends CardEnvironment          # game.gd            — NOT @tool
extends Control                  # game_view.gd       — NOT @tool
extends Control                  # play_area.gd       — NOT @tool
class_name LightLayer            # light_layer.gd     — NOT @tool
class_name SpotlightDirector     # spotlight_director.gd — NOT @tool

$ sed -n '/^\[autoload\]/,/^\[/p' project.godot
PseudoLocalisationCycler, SettingsManager, RunManager, LeakSentinel
```

**Two independent blockers, either one sufficient:**

1. **A non-`@tool` script loads in the editor as a PLACEHOLDER instance.** Calling a method on one
   fails outright — *"Attempt to call a method on a placeholder instance"*. `fx_editor.gd`'s own
   header documents this and it is why `FxStyle`, `FxRequest`, `FxFire`, `FxJuggle`, `ParticleSpec`,
   `ParticleEngine` and `FxAttachment` all carry `@tool`. So in the editor the tool could not call
   `Game.next()`, `Game.submit()`, `PlayArea.flush_rebuild()` or `LightLayer.set_lights()`.
2. **The editor instantiates NO autoloads.** `SettingsManager` and `RunManager` are absent, and
   `SpotlightDirector._on_section_changed` reads `SettingsManager.settings.card_scale` on every
   light, `LightLayer._settings()` reads it every frame, and the harness pattern starts a run with
   `RunManager.new_run(...)`.

⚠ **The escape everyone reaches for — "just mark them `@tool`" — is the worst available option and
this project already has the scar.** `@tool` on a resource script makes the editor write back only
the properties it could see and **silently drop the rest**; that is how `fire_card.tres` lost its
`pixel` and `dither` on 2026-07-28, and `PLAN.md` §1.8 carries the warning for exactly this reason.
Marking `Game` `@tool` is categorically worse than that: it runs the scoring cascade, the mod
dispatch and the save system inside the editor process every time the scene is open.

## What the design says, and where the two answers came from

They were asked in different breaths and never composed. `Q176` is in §17.15, about the tool's
**form**; `Q174`/`Q175` are two questions earlier, about its **fidelity**. Each is individually
right. Nothing asked what fidelity costs the form — which is the same composition failure as
GAP-006, where `QR2`=(d) and `Q16`=(c) were each correct and their product was a dim nobody chose.

## What it does not say

**How live knob dragging happens if not through the inspector.** `Q176`=(a)'s stated PURPOSES are
two, and both survive without `@tool`:

- *"live knob dragging"* — an in-scene control panel does this **better** than the inspector for a
  running tool, because **inspector edits do not reach a running scene at all**. `fx_editor` polls
  its resources (`WATCH_SECS`) precisely because it previews in the EDITOR, where the inspector is
  the only surface. A tool that runs does not have that constraint.
- *"runnable so an agent can screenshot it without opening the editor"* — unaffected.

## Options I can see, in the questionnaire grammar

- **(a)** **Runnable-only, with its own in-scene control panel.** Drop `@tool`. The tool is a scene
  you run; sliders, a scenario dropdown, play/step/freeze and a viewport-size control live in the
  scene itself and write straight to `PlayerSettings` and the glow `.tres`. Consequence: `Q174`,
  `Q175` and the no-mocks rule are satisfied exactly; both of `Q176`'s purposes are met; knobs are
  tunable **while a scenario runs**, which the inspector could never do. Cost: `Q176`=(a)'s letter is
  not honoured, and the knobs are a panel someone has to build and keep in step with §16.
- **(b)** **Two tools.** A `@tool` static preview (one card, the light layer, no `Game` — the fidelity
  `fx_editor` has) plus a separate runnable scenario player. Consequence: honours every answer
  literally. Cost: two things to keep in step, and the `@tool` half cannot show a cascade, a travel,
  a reveal or a dim pulse — i.e. it cannot show anything S18 was actually asked for. It would be a
  second FX editor wearing the spotlight's name.
- **(c)** **Make the game classes `@tool`.** Consequence: honours every answer literally and in one
  tool. Cost: the silent-property-drop trap above, game logic executing in the editor, and a
  permanent constraint on five core scripts to serve one tool. **I do not recommend this at any
  price and would want it declined explicitly rather than left open.**
- *my recommendation* **(a)**. It is the only option where the thing the owner said they wanted —
  *"I would rather do all testing via the planned editor so dont ask me to check until it exists"* —
  is what gets built, and it costs a letter rather than a capability. The in-scene panel is also the
  only surface that can tune a knob **mid-cascade**, which is exactly what tuning the GAP-006 pulse
  needs: the whole cycle is 1–3 frames, so stopping to edit the inspector between runs is the slow
  loop this tool exists to remove.
