## The symptom, and why every test stayed green

`SpotlightDirector` (S14) draws whatever `CardEnvironment.spotlight_cued(cards)` carries. That signal
is emitted by the activation sweep — and the sweep filters it:

```gdscript
# Scripts/card_environment.gd:156
var skill : CardModifierSkill = data.skill
if skill:
    if not skill.spotlit and skill.is_spotlit():
        skill.spotlit = true
        if skill.has_method(&"on_spotlight"):   # Q246=a
            cued.append(data)
```

**Two filters, and a real board survives neither.** A card is only ever cued if it has a `skill`
AND that skill implements `on_spotlight`. Measured on the shipped tree:

```
$ grep -rn "func on_spotlight" --include=*.gd . | grep -v /Tests/
./Cards/Skills/Rules/zone_adder.gd:21:func on_spotlight() -> void:
```

**One implementation in the entire game, and it is on a RULES-deck card.** Rules cards are
unconditionally spotlit (`CardModifier.is_spotlit()`'s first branch), so it transitions exactly once,
at startup, and never again — and it has no `CardVisual` in `PlayArea.data_card`, so
`SpotlightDirector._visual_of()` returns null for it and the light set comes out EMPTY anyway.

⚠ **So `set_lights()` never receives a non-empty set in a real game: no beam, no circle, and the dim
never rises. Ever.** Ordinary numeral cards — which is what a scored row or column is made of — have
no skill at all and are invisible to this path.

⚠ **The suite cannot see this and is not at fault for missing it.** Every spotlight test supplies
`Tests/Support/spotlight_test_skill.gd`, which *does* implement `on_spotlight`, so the cue fires and
`test_the_spotlight_wire_lights_the_layer` genuinely lights the layer. The fixture is the only reason
the signal has any content. **This is the same shape as the `bind()` bug S14's own notes describe** —
a wire that is green end-to-end against a fixture and inert against the game.

## What the design says

The two things have been conflated, and the design keeps them apart:

| | **Chart T — the momentary cue** | **The scoring beam** |
|---|---|---|
| Answers the question | *which cards have a TALENT to announce* | *which cards are being SCORED right now* |
| Design nodes | chart T, `Q246`=(a), `Q245`=(c) | `Q16`=(c), chart E, chart H/I |
| Correctly filtered to skills with a hook | **yes — that is the point** | **no** |
| Plan step | **S15** | **S14** |
| Lives in game state as | the `spotlight_cued` signal | `GameData.forced_spotlight` + `ScoringSection`, both shipped in S5/S9 |

`Q246`=(a) is right about what it was asked: a skill with nothing to announce should not flash. But
`Q16`=(c)'s travelling light is *"stays up for the whole act"* and *"moves from section to section"* —
a statement about the SECTION being scored, whose membership is every card in that row or column
whether or not it has a talent. Chart E's travel is between sections, not between talents.

**S14 was built on S15's signal.** Nothing in `PLAN.md` §2 actually says the scoring beam is fed by
`spotlight_cued`; S14 is specified as *"Per §1.10's origin rules"* and S15 as *"Draw what S10
emits"*. The director doing both is an implementation invention, and it is the fourth instance of
`DESIGN.md` v9's changelog pattern — a contract written where no answer covered it.

## What it does not say

**Which seam the beam reads.** `forced_spotlight` and `ScoringSection` are both live in `Game` and
both already carry exactly the right membership, but neither is exposed to the view layer: S5 writes
`forced_spotlight` and S9 clears it, and no signal announces either.

## Options I can see, in the questionnaire grammar

- **(a)** **A second signal for the section.** `Game` emits `spotlight_section_changed(cards)` as the
  activation sweep begins each section and an empty set at `_release_spotlight()`. `SpotlightDirector`
  draws THAT for the beam; `spotlight_cued` stays exactly as it is and becomes S15's business alone.
  Consequence: the two questions stay two signals, chart E's travel becomes trivial (each emit IS a
  section change, so it is the natural place to ease from the previous set), and `Q246`=(a) is
  untouched. Cost: one new normative contract on `Game`, which is what the handoff warns to have
  reviewed before writing.
- **(b)** **Widen the existing cue** — drop the `has_method(&"on_spotlight")` filter so every card
  that becomes spotlit is cued, and let S15 do the talent filtering at the drawing end.
  Consequence: one signal, no new contract. But it overturns `Q246`=(a) rather than sidestepping it,
  and it makes the cue fire for every card on the board on the first sweep of every act — the momentary
  flash would land on all of them, which is precisely what `Q246` was asked to prevent.
- **(c)** **The director reads `forced_spotlight` directly**, polling it in `_process` instead of
  listening for anything. Consequence: no new signal at all and it cannot fall out of step with the
  state, since it IS the state. But it is a per-frame dictionary walk over the board, the view layer
  reaches into `GameData` (which the Game/GameView split exists to prevent), and there is no edge to
  hang chart E's travel easing on — the director would have to diff the set itself to find one.
- *my recommendation* **(a)** — it is the only option that keeps the two questions apart, and they
  really are two questions: `Q245`=(c) already gives the cue its own shallower dim *outside* scoring,
  which only makes sense if the cue and the scoring beam are separate events. It also puts chart E's
  travel edge exactly where the easing needs it.
