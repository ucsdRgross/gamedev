# GAP-009 — a pad or keyboard player cannot reach Undo from the outcome screen
status: answered
raised: at the close review (S24), traced as close fix 8 and measured there
design: DESIGN.md §4; answers Q109; the multi-modal hard project rule
severity: OWNER CALL (a pad player can finish every show; only the rewind is out of reach)
owner ruling: takes the recommendation, option (b) - "an Undo button inside the win/lose screen beside Continue, in the same SubViewport". The owner's words: "i will
take recommendation for all gaps". Build it; the work item is in HANDOFF_sidebar_gaps.md.

**What the design says** — `Q109`=(a): "unchanged — undo rewinds the automatic end exactly as it
rewinds a manual one, and the player is back on the live board". The project's hard rule is
multi-modal input: a pad or keyboard player must never need the mouse (`Q137`'s own note: "multi-modal
input is a hard project rule").

**What the code does** — measured in TestSidebar's real `Main` fixture, with pad buttons pushed
through the root viewport. Goal 0, one placement by pad A: the win screen comes up and Continue, in
the game picture's SubViewport, holds the focus. The root viewport's focus owner is null. Undo is
visible and `FOCUS_ALL` in the root HUD. After d-pad up, left, right and down, the SubViewport's
focus owner is still Continue and the root's is still null. L1 (`wall_back`) zooms the board out to
the overview, and after four more d-pad presses the focus is still on Continue with the root owner
null. Godot's focus navigation never crosses a viewport, and `project.godot` binds no undo action.
Undo is reachable only by mouse or touch.

**Options I can see** — **(a)** an `undo` input action bound on pad and keyboard (for example a
shoulder or face button and Ctrl+Z). `GameView` reads it wherever the show is, so it rewinds the
outcome and any live placement alike, and nothing on screen changes. The player has to learn the
binding, and a stray press rewinds · **(b)** an Undo button inside the win/lose screen beside
Continue, in the same SubViewport, so the d-pad walks Continue ↔ Undo. The player sees two buttons
where there was one. The HUD's Undo stays for the mouse, so Undo shows twice while the outcome is
up · **(c)** as built: the outcome's Undo is mouse/touch only, and L1 does not help · *my
recommendation* (b). It is the only option a player can discover on the screen that needs it, it adds
no binding, and it reuses `GameView._on_undo_pressed` exactly as the HUD button does.
**Blast radius** — (a) `project.godot` input map, a `GameView` input reader, the settings
remap screen if one lists actions · (b) `Levels/game_view.gd` (`_on_show_resolved` builds a second
button beside Continue, `_on_show_unresolved` frees it), focus neighbours between the two, a
localisation row if the label is not the HUD's own · both: a TestSidebar row that reaches Undo from
the outcome by pad and asserts the rewind
**Meanwhile** — as built (c)
