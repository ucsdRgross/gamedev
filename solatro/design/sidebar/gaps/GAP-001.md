# GAP-001 — a 16:9 window wider than 2560 px clamps the container, so the inset is not 394 there
status: built
raised: during S3 (brief preparation)
design: DESIGN.md version 10, nodes D6, D7, D8, D10
severity: CONTRADICTION
owner ruling: takes the recommendation, option (b) - "the cap applies only when the window is WIDER than the picture's aspect, so every 16:9 window keeps 394 and only ultrawides clamp". The owner's words: "i will
take recommendation for all gaps". Built, one commit per gap, on branch `sidebar`.

**What the design says** — DESIGN.md, the arithmetic under Flowchart D: *"At the picture's own
aspect the window cancels out entirely ... exactly today's measured `board_inset_left`, at any 16:9
window size."* PLAN.md S3's done-when repeats it: *"`board_inset_left == 394.0` at a 16:9 window of
any size"*. Both sit beside the normative clamp in PLAN §1.1,
`container_px := min(settings.container_size_fraction * reference, settings.container_size_max_px)`,
with `container_size_max_px` defaulting to 640 (DESIGN.md §5 Tunables, NAMES.md §5).

**What the ANSWER says** — `Q50`=(c): *"it is clamped, and the clamp is measured inward: "maximum
width from right to left, so hud stays near middle.""* — asked about *"A very wide window (32:9)"*.
`Q23`=(a): *"a fraction of the WINDOW's width, independent of the picture"*. `Q246`=(a): *"one knob, a
fraction of the WINDOW"*. None of them names the cap's value or says whether a 16:9 window may reach
it; the 640 default is the design's own number, not an answer.

**What it does not say** — whether a large 16:9 window (anything wider than 640 / 0.25 = 2560 px,
e.g. a 3840×2160 4K display) should clamp. As specified it does: the container is 640 window px,
a sixth of the screen instead of a quarter, and `board_inset_left` is 640 / (3840/1576) = 262.7, not
394. "394 at any 16:9 window" and "clamp at 640 window px" cannot both hold above 2560 px wide.

**Why it blocks** — the design contradicts itself (protocol item 3), and the two readings differ in
what a 4K player sees: a quarter-width HUD, or a sixth-width one. It does NOT block building S3:
§1.1 is implemented exactly as written and TEST_PLAN 3.1's fixtures (1280, 1920, 2560 wide) all sit
at or under the clamp.

**Options I can see** — **(a)** keep the clamp as specified — a 16:9 window wider than 2560 px gets a
640 px container and a narrower inset; "any 16:9" in the docs is corrected to "up to 2560 px wide" ·
**(b)** the cap applies only when the window is WIDER than the picture's aspect, so every 16:9 window
keeps 394 and only ultrawides clamp — the cap becomes a rule about shape, not about pixel count ·
**(c)** keep the rule, raise the `container_size_max_px` default so no common 16:9 display reaches it
(e.g. 960, the value at 3840 px wide) — ultrawides clamp later and less · *my recommendation* (b),
because `Q50` asked about 32:9 and the arithmetic's point was that the authored shape does not move
**Blast radius** — plan step S3; design nodes D6, D7, D8, D10; TEST_PLAN 3.1, 3.2
**Meanwhile** — S3 builds §1.1 exactly as written and tests the TEST_PLAN fixtures; nothing is
parked

**As built** — `HudContainer._container_px` caps at `container_size_max_px` only where the band's axis outruns the project's reference window shape (`PlayArea.reference_window_size()`, the project's own 1152x648, not the game picture's 1576x887 — the picture is fractionally narrower than 16:9, so a rule phrased against it would clamp 4K). Every 16:9 window keeps its 394 px inset; only an ultrawide, or an ultratall under the top band, clamps. TEST_PLAN 3.1 gained the 3840x2160 fixture.
