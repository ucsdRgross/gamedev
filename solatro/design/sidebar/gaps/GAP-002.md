# GAP-002 — the board inset ignores the covering picture's crop, so a narrow window puts board under the container
status: built
raised: during S3
design: DESIGN.md version 10, nodes D8, D10, D2, D4
severity: CONTRADICTION
owner ruling: takes the recommendation, option (a) - "measure the board's region in the VISIBLE picture: every inset gains the crop on its axis". The owner's words: "i will
take recommendation for all gaps". Built, one commit per gap, on branch `sidebar`.

**What the design says** — D8: *"PlayArea.board_inset_left becomes the container's width, converted
from window pixels to picture pixels through the focused picture's live scale"*. D10: *"the board
centres in what is left, never on the screen"*. PLAN §1.1 (normative):
`PlayArea.board_inset_left := container_px / picture_scale`, with
`picture_scale := max(window.x / 1576.0, window.y / 887.0)  # a focused picture COVERS`.

**What the ANSWER says** — `Q24`=(a): *"exactly the HUD's own width, whatever it is — the sidebar
covers the HUD and nothing else, by construction"*, whose note calls (a) *"the only one that cannot
ever cover a card"*. `Q27`=(d), owner note: *"center of screen for picture is center of remaining
space not taken by sidebar."* `Q49`=(d), owner note: *"main playing window should be like a square
whenever possible."* None of them says how the board's region is measured when the covering picture
is cropped.

**What it does not say** — a covering picture is CROPPED whenever the window is narrower than
1576:887 (16:10, 4:3, every portrait window — exactly the windows that trigger the top case). §1.1
converts `container_px` as a LENGTH, but the inset is a POSITION measured from the picture's edge;
the picture's edge is off-screen by `crop_x = (1576 - window.x / picture_scale) / 2`. Measured
consequences:
- 1920×1200 (16:10): scale 1.353, crop_x 78.4 picture px. The board region starts at 354.8 picture
  px, but the container's right edge is at 78.4 + 354.8 = 433.2 — the region's first 106 window px
  sit under the container, and its last 106 window px are off-screen right. (The centre is still
  right, so a narrow board may not visibly overlap.)
- 600×1000 (portrait, top case): only 532 of 1576 picture px are visible across; the board is laid
  out against all 1576. ⚠ The board's spill UNDER the band seen there is NOT this gap: the Phase 1
  review found `PlayArea.focused_board_zoom()` solving its height against the whole PlayArea while
  `_board_window_local()` subtracts `board_inset_top` — a bug, fixed under S3's own rule (D9, D10).
  This gap covers only the horizontal crop.
At 16:9 and at 32:9 `crop_x` is 0, so the S3 hard gates (394, 262.7) hold either way.

**Why it blocks** — §1.1 is normative and cannot be changed by the executor, the design's intent
(D10, `Q24`) contradicts it on every window narrower than 16:9, and the fix needs names NAMES.md does
not fix (the board's fit needs a right/bottom edge, or a visible-region input to `PlayArea`).

**Options I can see** — **(a)** measure the board's region in the VISIBLE picture: every inset gains
the crop on its axis (`board_inset_left := crop_x + container_px / picture_scale` on the side,
matching right/bottom insets of `crop_x`/`crop_y`), so the board fits and centres in what the player
can see beside the container — 16:9 and 32:9 unchanged · **(b)** keep §1.1 literally — on 16:10, 4:3
and portrait windows part of the board's region is under the container or off-screen · **(c)** the
GAME picture CONTAINS the window instead of covering it on narrow windows (letterboxed), so nothing
is cropped — changes the wall's look and is outside this plan's scope · *my recommendation* (a)
**Blast radius** — plan steps S3 (and S4 only if the map's container overlaps map content — it uses
`container_px` directly, so probably not); design nodes D8, D9, D10; TEST_PLAN 3.1–3.3 values unchanged
**Meanwhile** — parked: fitting the board to the visible region (the top-case "no card under the
container" check is not added). Continued: S3's other defects, and S4 onward

**As built** — the board's region is measured in the VISIBLE picture. `WallPicture.visible_rect_beside` holds the one copy of the crop arithmetic and `local_rect_beside` delegates to it; `PlayArea.board_visible_crop` is the far-edge reserve. TEST_PLAN 3.5 asserts the board's region both clears the container and FILLS the width left beside it, at 16:10, 4:3 and portrait.
