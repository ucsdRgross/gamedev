# GAP-007 — after a failed drag the card is "no longer following" for exactly one mouse motion
status: answered
raised: at the Phase 5 boundary review (S14–S18)
design: DESIGN.md §1.6, nodes E15–E17; answers Q262, Q281
severity: OWNER CALL (two rulings contradict for the mouse; not blocking)
owner ruling: takes the recommendation, option (a) - "after a failed drag, following restarts only on a NEW press, not on motion". The owner's words: "i will
take recommendation for all gaps". Build it; the work item is in HANDOFF_sidebar_gaps.md.

**What the design says** — `Q281`=(a): a release over an illegal cell sends the card "back to its
slot, still armed, still lifted, and no longer following — so a failed drag costs nothing". The
owner rejected (c): "back to its slot, armed and lifted, and still following the pointer", with the
note "(c) would leave the card chasing a finger that is no longer touching anything". `Q262`=(a):
following starts on "any mouse motion at all".

**What the code does** — both, literally. `_release_places` calls `stop_following()`; the next
`InputEventMouseMotion` reaches `_on_pointer_moved`, which ends with an unconditional
`follow_cards()`. A mouse player who drags onto an occupied cell, releases and moves one pixel sees
the card resume chasing the pointer from wherever it was — `Q281`=(c), the rejected option. On
touch the return holds, because no motion arrives between finger lifts. `drag_release_returned.png`
was captured with the pointer parked, so the by-eye row could not show it.

**Options I can see** — **(a)** after a failed drag, following restarts only on a NEW press (a
click or a touch), not on motion — `Q262`'s "any motion" applies to a card that has never been
carried this gesture · **(b)** following restarts on motion that leaves the card's cell (the same
crossing S15 uses for the description), so a twitch does not re-latch but a deliberate move does
· **(c)** as built: the return is one motion long on the mouse · *my recommendation* (a) — it is
the owner's own note applied to the mouse
**Blast radius** — `UI/play_area.gd` (`_on_pointer_moved`, `_release_places`); TestDragPlace 5.3
gains a "then move the mouse" half; DESIGN §1.6 text
**Meanwhile** — as built
