# GAP-005 — Every shoulder button is already bound, and the layer view was ruled onto one
status: open
raised: during S13 (the layer view)
design: solatro/design/board-plan/DESIGN.md version 1, nodes F4–F8; PLAN.md §1.10 (the layer view
row), NAMES.md (the `ui_plan_layer` InputMap action)
severity: GAP

**What the design says** — PLAN §1.10: the layer view is *"opened by a **held shoulder button AND a
HUD control** every input mode reaches"*. NAMES.md fixes the action as `ui_plan_layer` — *"held to
peek, and bound for keyboard, mouse and controller alike"*.

**What the ANSWER says** — `Q117`=(c), **both** of *"(a) a shoulder button held, matching `Q114`'s
peek"* and *"(b) a button on the HUD that keyboard, mouse and controller all reach the same way"*.
`Q114`=(c), **both**: *"hold for a peek, click to stay"*. Neither names WHICH shoulder, and neither
was asked against this project's InputMap.

**What it does not say** — which controller button the held peek takes, when the pad has four
shoulders and all four are spoken for:

| button | action | also |
|---|---|---|
| L1 (`button_index` 9) | `wall_back` | read inside a show as zoom OUT one level |
| R1 (`button_index` 10) | `wall_forward` | read inside a show as zoom IN again |
| L2 (`axis` 4) | `grid_pan_left` | — |
| R2 (`axis` 5) | `grid_pan_right` | — |

The free buttons are the face button X (2), Guide (5), Start (6) and the two stick clicks L3 (7) /
R3 (8) — none of which is a shoulder.

**Why it blocks** — it is an owner call about controls (triage 2), and every option is visible in
the product. The board itself reads L1/R1 while a show is focused
(`PlayArea._consume_as_view_action`), so binding the layer view onto one would make a single press
do two things at once; and the poker-patience design already ruled on exactly this collision —
`Q187`=(b), *"new actions on different bindings (say L2/R2 …), leaving the wall's shoulder buttons
alone"* — with a shipped test (`Tests/UI/test_grid_view.gd`, the panning-actions row) asserting that
`wall_back` / `wall_forward` keep their own bindings. Choosing for the owner would either overturn
that ruling or quietly drop half of `Q117`=(c).

**Options I can see** —
**(a)** **L3 or R3, the stick click, held** — consequence: a free binding today, reachable without
letting go of either stick, but it is not a shoulder and a click-to-peek is easy to trigger by
accident while aiming a stick ·
**(b)** **the face button X (2), held** — consequence: free today and unmistakable, but it sits
under the thumb that also drives Accept, so a peek competes with selection ·
**(c)** **rebind `wall_back` / `wall_forward` off L1/R1** (onto the stick clicks, say) and give the
layer view a real shoulder — consequence: `Q117`=(c) is honoured exactly, at the cost of relearning
the wall's Back/Forward and re-deriving the poker-patience ruling and its test ·
**(d)** **double-bind L1**, with the layer view taking it first while a show is focused —
consequence: no new button to learn, but one press zooms the board out AND opens the layer, which is
the surprise `Q187` was written to avoid ·
**(e)** **the controller reaches the layer view through the HUD control only** (focus + Accept),
dropping the held-shoulder half of `Q117`=(c) — consequence: nothing to rebind and every input mode
still reaches the view, but the controller loses the PEEK: it can toggle, not hold ·
*my recommendation* (a) — it is the only option that costs no existing binding, keeps the peek, and
can be moved later by editing one line of `project.godot`.

**Blast radius** — `project.godot`'s `[input]` block (one event added to `ui_plan_layer`), and the
held-controller half of TP-68 in `Tests/UI/test_plan_visuals.gd`, which is one more route through
the driver the other three already use. Option (c) additionally touches `wall_back` / `wall_forward`
and the panning-actions row of `Tests/UI/test_grid_view.gd`. No production logic branches on the
binding: `PlayArea` asks the ACTION, never a keycode.

**Meanwhile** — parked: the held CONTROLLER route, and the half of TP-68 that would drive it.
Everything else in S13 shipped: `ui_plan_layer` carries a keyboard binding (`M`, the only owner-
visible choice this step made, logged in `ASSUMPTIONS.md`), the held peek works on the keyboard, and
the HUD control answers a mouse click, a keyboard Accept and a controller Accept — so the layer view
is reachable from a pad today, just not held from one.
