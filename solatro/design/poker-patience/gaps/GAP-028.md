## What was measured

```
fixture: 5 grids, pitch 1219, middle of five at cell-block local x 2462
design canvas 3656 wide -- sized for grid_max_count = 3 -- its centre 1828
camera visible = [-596.95, 596.95]   grid 2 maps to [634, 850]
850 - 596.95 = 253.05   -- exact
```

`TP-138` reads the **cell block** (216x286) via `pa._cells_root(panel)`, which is correct — the
"panel vs cell block" hypothesis was wrong. It compares against `WallTransition.visible_rect()` off
the real `%Camera2D`, which is also correct.

**The mismatch is the fixture's grid count against the canvas's budget.**
`PlayArea.game_picture_design_size()` (`UI/play_area.gd:178`) is documented: *"DERIVED FROM THE CAP
AND THE DEFAULT GRID SHAPE, NEVER FROM THE GRIDS A RUN HAS"* — 3656 px, exactly `grid_max_count`
positions. Production enforces the cap at `Cards/Skills/Rules/skill_grid_allotment.gd:36`.
`_stand_up_main_grids(5)` calls `Board.add_grid()` directly and bypasses it, so the middle of five
positions no longer coincides with a canvas built for three.

At 3 grids the same check passes: blocks at `504 / 1723 / 2942`, span centre `1831` against the
canvas's `1828`.

## ⚠ THE PART THAT IS NOT A TEST BUG

**The five-grid fixture is DELIBERATE.** The handoff records it: *"`TP-106`'s FIXTURE IS FIVE GRIDS
ON PURPOSE — `grid_max_count` governs UNLOCKING, not `Board.add_grid`"*, because `H24` —
*"with more than 3 grids, panning shifts WHICH 3 are in frame"* — is carried by the design even
though `Q7` caps grids at 3 today.

So the measurement also says: **`H24` and a fixed three-position picture are in tension.** Grids
beyond position 3 fall outside the design canvas, and content outside the canvas is never rendered
into the SubViewport at all — the same "a camera can only crop pixels that exist" constraint that
forced `GAP-024`=(b). ⚠ `Q166`=(a) explicitly rejected sizing the picture from the actual grid count
(*"`design_size` stays AUTHORED data sized for exactly 3 grids, NOT computed at show start"*), which
closes the obvious escape.

**Nobody has ruled on how `H24` is supposed to work under that constraint.** It is unreachable in the
shipped game (`Q7` caps at 3), so it costs nothing today — but the test that exercises it is failing
for exactly this reason, and the next person will re-diagnose it.

## Options for the `H24` half — UNANSWERED

- **(a) `H24` is deferred while `Q7` caps at 3.** Mark the >3-grid checks as exercising an
  unreachable case, and revisit if the cap ever lifts. Cheapest and honest.
- **(b) The picture grows with the cap**, so `grid_max_count` 4+ widens the canvas. ⚠ Measured
  earlier: at `grid_max_count` 4 the render clamp BITES (6096 -> 4096) and `size_2d_override` holds
  the layout — so this has a hard ceiling.
- **(c) `H24` means the BOARD scrolls within a 3-position picture** rather than the picture holding
  every grid — the scroller's `H13`/`H23` job extended. Needs the clipping question answered again.
