# GAP-006 — How do the per-cell buckets enter `grid_score`'s product?

status: resolved
outcome: answered
raised: 2026-08-26, during execution plan step S13 (grid_score as the product of positive buckets)
design: PLAN.md §1.6 (`QR5`, `Q322`); GAP-005 (the owner's per-cell bucket answer)
severity: GAP

## OWNER ANSWER — the height scores FOLD INTO the special term

Owner, verbatim:

> *"have all height scores be added to the special when doing grid score, so its row x col x
> special (diag and height) x combo, row and col scores from different height levels still go
> in their row and col buckets"*

The rule this produces:

    grid_score = row_term x col_term x special_term      (each included only when > 0)

    row_term     = the grid's height-0 row bucket     + every raised row bucket
    col_term     = the grid's height-0 column bucket  + every raised column bucket
    special_term = the grid's special bucket (diagonals) + every CELL bucket in that grid

    board_total  = sum of grid_score over grids
    displayed    = board_total x combo                   (combo applies at DISPLAY time)

So the product stays **three factors**, exactly as `Q322`'s worked example walks it. None of
(a)-(d) as written: the cell buckets are not a fourth factor, not the max, and not excluded —
they are **summed into the special term**, alongside the diagonals.

⚠ **The granular buckets still exist and still matter.** This answer changes only how the
buckets COMBINE at scoring time. Per-cell buckets remain per cell because a height score label
sits above each stack, and raised row/column buckets remain per height, because each has its
own label too. **Storage is granular for the labels; scoring aggregates.** That is the same
shape the per-cell answer already established, applied one level up.


## What the design says

`PLAN.md` §1.6 is explicit about the shape of a grid's score:

```
grid_score  = product of every bucket whose value is > 0
            = 0 when no bucket is > 0
```

and the owner's worked example (`Q322`) walks it with **three** buckets:

> *"row + col + diag = 0 + 0 + 0. Row gets 10 score. it is now 10 + 0 + 0 = 10. Col gets 5
> score. It is now 10 \* 5 + 0 = 50. Diag gets 2 score. It is now 10 \* 5 \* 2 = 100."*

Three buckets, so at most three factors.

## What the repo says

GAP-005's answer added a fourth KIND of bucket, and it is not one per grid — it is **one per
cell**. A default 5×5 grid therefore has up to **25 cell buckets** alongside row, col and
special.

## What it does not say

Whether a cell bucket is a factor in the product at all, and if so how many factors there are.

## Why it matters — this is not a style question, it is an overflow

Under the rule as literally written, every cell bucket with a value above 0 is its own factor.
A grid with all 25 cells stacked to 5 would multiply **28 numbers together**. Even at a modest
50 points per stack that is on the order of 50²⁵ — the score stops being a number a player can
read, and `BigNumber` exists precisely because this economy already runs large.

The worked example cannot settle it: it predates the per-cell answer and covers only the case
where no stack has scored. **Both readings reproduce it exactly**, which is what makes this a
real fork rather than an oversight — the case that separates them is the one the example does
not contain.

## Options I can see

- **(a)** The cell buckets **sum into one fourth factor**: `row × col × special × (sum of every
  cell bucket)`. Keeps the product to four terms and keeps a grid's score readable, and reads
  naturally as "the height score" as one thing — which is how the design already talks about
  it. Costs the per-cell granularity at scoring time, though the per-cell labels still show
  their own numbers.
- **(b)** Every cell bucket is **its own factor**, exactly as §1.6 is written. Most literal
  reading, and makes tall builds explosively strong — which may be the intent, since a stack of
  15 is expensive to build. Costs: the number leaves human scale almost immediately, and the
  goal curve (`goal_g0` / `goal_alpha`, Phase 9) would have to be refit against a very
  different distribution.
- **(c)** The cell buckets **take the max, not the sum or the product**: `row × col × special ×
  (tallest cell's score)`. Rewards the single deepest stack rather than many shallow ones,
  which matches the "one impressive tower" fantasy, and stays readable.
- **(d)** The cell buckets are **not part of `grid_score` at all** — they feed their own label
  and their own total, banked straight into the board total. Keeps `Q322`'s three-factor
  product exactly as answered and leaves the vertical game as a parallel economy.

**Blast radius** — `GameData.grid_score()` and `board_total()` (S13); the HUD's two live
numbers (§1.6); Phase 9's goal-curve refit, which cannot be fitted until this is decided.
