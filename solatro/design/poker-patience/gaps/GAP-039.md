# GAP-039 — isolation, exactly-three, and no-clipping cannot all hold; the clipping IS the slack

status: open
raised: implementing the focused-framing fix (`C + D` of the framing options)
design: `PLAN.md` §1.2 (`Q13`=d), §1.13 (`H1`, `Q166`=a), `DESIGN.md` §36 (`H6`), `TP-113`, `TP-140`
severity: THREE SHIPPED CONTRACTS ARE MUTUALLY UNSATISFIABLE at the current block and strip sizes

## The three contracts

1. **Isolation** (`TP-140`, owner ruling): focusing a grid takes its neighbours out of frame.
2. **Exactly three** (`TP-113`, `Q166`=a): the picture holds three grids and is **not wide enough
   for a fourth**.
3. **No clipping** (owner): *"clicking on grid zooms in but everything is clipped instead of
   fitting in 5x5 grid + entrance row as minimum size."*

## They cannot all hold — and the margin cannot buy the slack

Let `B` = a grid block's width (216), `S` = block height + Entrance strip (286 + 81 = 367),
`r` = `ref_h / ref_w` (0.5625), `W` = the picture's width, and `b = (W - 3B)/4` the one buffer
(the gap between grids and the gap at the picture's edge are the same quantity).

- **(2)** ⇒ `W < 4B + 3b` ⇒ **`W < 7B = 1512`**.
- **(3)** ⇒ the board's zoom fits what the CAMERA shows: `z = W·r / (m·S)`, where `m` is whatever
  crop the camera applies.
- **(1)** ⇒ `z·(b + B/2) >= W / (2m)`.

Substituting, **`W` and `m` both cancel**:

```
b >= S/(2r) - B/2 = 367/1.125 - 108 = 218.22      ->   W >= 3B + 4b = 1520.89
```

`1520.89 > 1512`. The feasible set is empty.

⚠ **`m` CANCELLING IS THE WHOLE POINT.** `wall_overfill_margin` looks like the thing buying the
current design its slack, and it is — but only because the board today is sized to the **picture's**
height while the camera shows less. **The clipping IS the slack.** Size the board to what the
camera actually shows and the margin stops helping at all.

## Measured at both corners, on the product's own path

| | `W` | isolation `TP-140` | exactly three `TP-113` | clipping |
|---|---|---|---|---|
| shipped | 1495 | ✅ | ✅ | ❌ block top cut **5.28 px**, Entrance bottom **11.28 px**, sides 14.66 |
| aspect-exact, margin dropped | 1536 | ✅ all four checks | ❌ *"1536.0 px, four grids span 1530.0 px"* | ✅ block fully framed, sides **0.00** |

The second row was built and run, not modelled: rounding the buffer up to the aspect step
(`aspect_exact_buffer`) and solving isolation at `m = 1`. It has been reverted.

## The question that actually decides it

**How much of the Entrance must the focused view frame — the whole configured strip, or one card
row?** `entrance_visible_rows` defaults to **1.5**, so the strip is 81 px where one card row is 54.
That 27 px is the entire difference between infeasible and comfortable.

With `S = 286 + 54 = 340`:

```
b >= 340/1.125 - 108 = 194.22   ->   W >= 1424.9,  and W < 1512 still holds
aspect-exact widths in that band: 1440, 1456, 1472, 1488, 1504
at W = 1440:  b = 198,  H = 810,  z = 810/340 = 2.3824
  isolation   2.3824 x (198 + 108) = 729.0  >=  1440/2 = 720   ✅
  no fourth   4x216 + 3x198 = 1458  >  1440                     ✅
  clipping    340 x 2.3824 = 810 == the picture's height, and 1440x810 is EXACTLY 16:9,
              so focused_scale() reads two equal ratios, applies no margin, and the camera
              shows the whole picture                            ✅
```

**All three hold.** Nothing else moves: same closed form, same one-buffer contract, same derivation.

## Options

- **(a)** The focused view must frame the 5x5 block plus **ONE CARD ROW** of the Entrance, not the
  whole configured strip. The strip stays a resting reservation; its real depth is already cleared
  by the board's floor rather than by the strip. Picture becomes 1440x810.
- **(b)** Keep framing the whole strip and **relax "exactly three"** (`Q166`=a) to "holds three".
  Picture becomes 1536x864, aspect-exact, no crop, isolation intact — measured working, and the
  only thing it costs is `TP-113`'s last check.
- **(c)** Keep framing the whole strip and **shrink `entrance_visible_rows` to 1.0**, which is (a)
  by a different route: the same numbers, but the player also sees less Entrance at rest.
- **(d)** Accept the clipping as the price of the other two, and close the owner's report as
  working-as-designed.

## What any answer must not break

- `TP-139` (the focused grid is as tall as its window), `TP-141` (a non-focused grid paints nothing
  outside the board window).
- The one-number contract: the gap between grids and the gap at the picture's edge are the same
  quantity, derived and not stored.
- `game_picture_design_size()` staying ONE fixed size for every run (`H1`).

## The instrument

`Tests/UI/test_grid_view.gd::run_the_focused_view_frames_the_block_and_the_entrance_test` asserts
contract (3) directly against the CAMERA's own visible rect, naming the clipped edge and the
pixels. **It is red today and that is correct** — it is the gate this gap is about, and it agrees
with `Tests/Visual/focused_pose_probe` to 0.01 px.

## Separately, and not fixed here

`GameView._apply_play_container_height()` writes `offset_bottom = offset_top + design.y` while
`offset_top` stays at its authored 3, so the play area spans **y 3..844 of an 841-tall picture** —
3 px past the bottom. It is why the Entrance's cut (11.28) is not the same as the block's (5.28).
Left alone so the numbers above stay comparable while this gap is open.
