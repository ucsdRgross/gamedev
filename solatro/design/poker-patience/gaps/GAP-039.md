# GAP-039 — isolation, exactly-three, and no-clipping cannot all hold; the clipping IS the slack

status: open
raised: implementing the focused-framing fix (`C + D` of the framing options)
design: `PLAN.md` §1.2 (`Q13`=d), §1.13 (`H1`, `Q166`=a), `DESIGN.md` §36 (`H6`), `TP-113`, `TP-140`
severity: THREE SHIPPED CONTRACTS ARE MUTUALLY UNSATISFIABLE at the current block and strip sizes

## The three contracts

1. **Isolation** (`TP-140`, owner ruling): focusing a grid takes its neighbours out of frame.
2. **Exactly three** (`TP-113`, `Q166`=a): the picture holds three grids and is **not wide enough
   for a fourth**.
3. **No clipping** (owner): *"clicking on grid zooms in but everything is clipped instead of
   fitting in 5x5 grid + entrance row as minimum size."*

## They cannot all hold — and the margin cannot buy the slack

Let `B` = a grid block's width (216), `S` = block height + Entrance strip (286 + 81 = 367),
`r` = `ref_h / ref_w` (0.5625), `W` = the picture's width, and `b = (W - 3B)/4` the one buffer
(the gap between grids and the gap at the picture's edge are the same quantity).

- **(2)** ⇒ `W < 4B + 3b` ⇒ **`W < 7B = 1512`**.
- **(3)** ⇒ the board's zoom fits what the CAMERA shows: `z = W·r / (m·S)`, where `m` is whatever
  crop the camera applies.
- **(1)** ⇒ `z·(b + B/2) >= W / (2m)`.

Substituting, **`W` and `m` both cancel**:

```
b >= S/(2r) - B/2 = 367/1.125 - 108 = 218.22      ->   W >= 3B + 4b = 1520.89
```

`1520.89 > 1512`. The feasible set is empty.

⚠ **`m` CANCELLING IS THE WHOLE POINT.** `wall_overfill_margin` looks like the thing buying the
current design its slack, and it is — but only because the board today is sized to the **picture's**
height while the camera shows less. **The clipping IS the slack.** Size the board to what the
camera actually shows and the margin stops helping at all.

## Measured at both corners, on the product's own path

| | `W` | isolation `TP-140` | exactly three `TP-113` | clipping |
|---|---|---|---|---|
| shipped | 1495 | ✅ | ✅ | ❌ block top cut **5.28 px**, Entrance bottom **11.28 px**, sides 14.66 |
| aspect-exact, margin dropped | 1536 | ✅ all four checks | ❌ *"1536.0 px, four grids span 1530.0 px"* | ✅ block fully framed, sides **0.00** |

The second row was built and run, not modelled: rounding the buffer up to the aspect step
(`aspect_exact_buffer`) and solving isolation at `m = 1`. It has been reverted.

## The question that actually decides it

**How much of the Entrance must the focused view frame — the whole configured strip, or one card
row?** `entrance_visible_rows` defaults to **1.5**, so the strip is 81 px where one card row is 54.
That 27 px is the entire difference between infeasible and comfortable.

With `S = 286 + 54 = 340`:

```
b >= 340/1.125 - 108 = 194.22   ->   W >= 1424.9,  and W < 1512 still holds
aspect-exact widths in that band: 1440, 1456, 1472, 1488, 1504
at W = 1440:  b = 198,  H = 810,  z = 810/340 = 2.3824
  isolation   2.3824 x (198 + 108) = 729.0  >=  1440/2 = 720   ✅
  no fourth   4x216 + 3x198 = 1458  >  1440                     ✅
  clipping    340 x 2.3824 = 810 == the picture's height, and 1440x810 is EXACTLY 16:9,
              so focused_scale() reads two equal ratios, applies no margin, and the camera
              shows the whole picture                            ✅
```

**All three hold.** Nothing else moves: same closed form, same one-buffer contract, same derivation.

## Options

- **(a)** The focused view must frame the 5x5 block plus **ONE CARD ROW** of the Entrance, not the
  whole configured strip. The strip stays a resting reservation; its real depth is already cleared
  by the board's floor rather than by the strip. Picture becomes 1440x810.
- **(b)** Keep framing the whole strip and **relax "exactly three"** (`Q166`=a) to "holds three".
  Picture becomes 1536x864, aspect-exact, no crop, isolation intact — measured working, and the
  only thing it costs is `TP-113`'s last check.
- **(c)** Keep framing the whole strip and **shrink `entrance_visible_rows` to 1.0**, which is (a)
  by a different route: the same numbers, but the player also sees less Entrance at rest.
- **(d)** Accept the clipping as the price of the other two, and close the owner's report as
  working-as-designed.

## What any answer must not break

- `TP-139` (the focused grid is as tall as its window), `TP-141` (a non-focused grid paints nothing
  outside the board window).
- The one-number contract: the gap between grids and the gap at the picture's edge are the same
  quantity, derived and not stored.
- `game_picture_design_size()` staying ONE fixed size for every run (`H1`).

## Separately, and not fixed here

`GameView._apply_play_container_height()` writes `offset_bottom = offset_top + design.y` while

Left alone so the numbers above stay comparable while this gap is open.

## ⚠ OWNER RULINGS SINCE, AND WHAT THEY COST

Three instructions arrived after this gap was filed, and all three are built:

1. *"play area container should match height of window view"* — `PlayContainer` now FILLS the view
   (anchors, no code), so it is the window's own height in the wall and in a bare `game_view.tscn`
   alike. `_apply_play_container_height()` is gone.
2. *"add 1 row full card height buffer to top and bottom of the play area"* — `board_edge_pad_rows`,
   default **1.0**, **0 turns it off** for a phone.
3. *"make sure the buffer - grid - gap - entrance - buffer works on any screen size"* — the focused
   fit is now `min(height fit, width fit)`, so a narrow screen is bound by width.

⚠ **RULING 2 DECIDES THIS GAP AGAINST ISOLATION, and the arithmetic above says why.** The buffer
adds two card rows to `S`, and the panel's own column-label gutter adds a third term this gap did
not count:

```
S = block 286 + gutter 27 + strip 81 + 2 x pad 54 + scroller band 8 = 510
b >= S/(2r) - B/2 = 510/1.125 - 108 = 345.3   ->   W >= 648 + 1381 = 2029
```

against `W < 1512` for "exactly three". The gap is no longer 9 px; it is **517 px**. No buffer, no
picture width and no margin can close it.

**Measured cost, full suite:** `TP-140` both halves red, `TP-139` red (*"the FOCUSED grid's cell
block is exactly as tall as the board's window"* — grid 363.4 vs window 407.9, which is now true BY
DESIGN: the window also holds the gutter, the two buffers and the scroller's band), and `TP-101`'s
no-cut-off-grid red by 6.4 px. The framing gate's cell-block half now **passes**.

⚠ **`TP-139`'s WORDING IS NOW WRONG, not just its value.** The contract it states — block == window
— was the definition of the focused fit before rulings 2 and 3. Rewriting a planned row is a gap,
not an implementer's call, which is why it is recorded here rather than edited.

**So the live question is narrower than the four options above:** isolation (`TP-140`) and
exactly-three (`Q166`=a) can no longer both survive alongside the owner's own framing. One of them
has to give, and option **(b)** — relax "not wide enough for a fourth" — is the only one of the four
that still reaches a feasible picture.

## ⚠ A FIFTH OPTION NOBODY LISTED — ISOLATE BY CLIPPING, NOT BY SPACING

Every option above buys isolation with PICTURE WIDTH: space the grids far enough apart that a
focused one pushes its neighbours past the camera's edge. That is what makes the trilemma, because
the buffer is also what "exactly three grids" caps.

**The board's scroll container already clips (`clip_contents = true`), and `TP-141` already requires
that a non-focused grid PAINT nothing outside the board's window.** So isolation can come from the
WINDOW instead: in FOCUSED mode make the board's window the focused panel's own width, centred in
the post-HUD space, and the neighbours are clipped out at any buffer.

- The buffer stops carrying isolation, so it can shrink to whatever spacing looks right. `W < 7B`
  is satisfiable again, the picture stops growing, and the render clamp stops being a worry.
- The owner's buffer, the post-HUD centring and no-clipping all survive unchanged.
- **`TP-140` measures POSITION, not paint** (`_camera_overlaps` compares `_grid_world_rect` against
  the camera's rect), so it would still fail while the player sees exactly what the ruling asked
  for. `TP-141` is the check that already asks the right question.

⚠ **So this is a decision about what "out of view" MEANS** — off-camera, or not painted. The owner's
words are *"focusing takes the other grids out of the window"*, which reads as paint. If that is the
intent, `TP-140` is the row that needs rewording and the whole width problem dissolves.

**Not built, and not costed beyond the above.** It is listed because the standing rule here is to
look for the option nobody wrote down before answering the four that were.

## ⚠ OWNER ANSWER — OFF CAMERA, and the fifth option is DEAD

> *"off camera. if an effect makes a card move between grids it should not disappear."*

So "out of view" means **off the camera**, not merely unpainted. `TP-140` asks the right question as
written and does NOT need rewording. **The clipping option above is withdrawn**, and the reason is
the more important half of the answer: isolation must never be bought with a clip, because a clip
that hides a neighbour also hides a card travelling to it.

### ⚠ THE CLIP IS ALREADY THERE, AND IT ALREADY THREATENS THAT

Read off `UI/play_area.tscn`, not inferred: **`%CardLayer` is a child of
`SmoothScrollContainer/TopLevelVBox`, and the scroller has `clip_contents = true`.** Every grid card
visual is therefore clipped to the board's WINDOW — and that window has just got smaller twice, by
the HUD's reserve and by the two card-row buffers.

So a card whose flight path leaves the board's window vanishes for the length of the move. Nothing
measures this yet; the owner has now said it must not happen.

⚠ **`TP-141` LEANS ON THAT SAME CLIP.** "A non-focused grid paints nothing outside the board window"
is true *because* the scroller clips. A window widened until a cross-grid flight stays visible is a
window that stops hiding the neighbour it was hiding. **`TP-141` and the no-disappearing rule are
the same dial**, and this gap now owns both ends of it.

### What remains

Options (a) and (c) were about how much of the Entrance the focused view must frame; the card-row
buffer ruling has overtaken them. Option (5) is dead. **Option (b) — relax `Q166`=a's "not wide
enough for a fourth grid" — is the only one left**, and with the buffer, the panel gutter, the
scroller band and the HUD reserve all now in the fit, the isolating picture width is far past where
this gap first put it:

```
S = block 286 + gutter 27 + strip 81 + 2 x pad 54 + band 8 = 510
the HUD reserve also shifts the board right by half of itself, which the left neighbour pays for
  z(b + B/2) >= W/(2 x wom) + hud/2      with z = W r / S, hud = 402
  -> quadratic in W, root at W ~= 2310, H ~= 1299
```

against `W < 7B = 1512` for "exactly three". `game_picture_max_render_px` is **4096**, so a 2310 x 1299 picture stays under the clamp and
`TP-114` is not at risk — checked, not assumed. What it costs instead is SHARPNESS: the wall camera
magnifies a fixed render target, so a picture that much larger than the window is minified at rest
and the focused board is drawn from fewer texture pixels per screen pixel than today.

## The no-disappearing rule now has a gate, and it is RED

`GRID VIEW::run_a_card_between_grids_is_never_clipped_away_test` asserts every grid's own cells sit
inside the board's CLIP window while another grid is focused. It checks the ENDPOINTS of a
cross-grid move, not a flight: if either end is outside the clip window then every path between
them is cut at that end, whatever curve an effect chooses, and a flight test would prove less while
depending on one effect's easing.

**Measured, three grids, focused on the middle one:**

```
grid 0 cells at x 121.4   clip window [402.0 .. 1152.0]   CULLED
grid 2 cells at x 1030+   clip window [402.0 .. 1152.0]   CULLED at the far edge
```

⚠ **THE CLIP WINDOW IS NOW NARROWER THAN THE BOARD IT HOLDS**, because the focused fit sizes it to
ONE panel and the HUD reserve pushes its left edge to 402. Both neighbours are outside it, so a card
sent to either one disappears for the whole move.

⚠ **THIS IS THE SAME DIAL AS `TP-141` AND THEY POINT OPPOSITE WAYS.** `TP-141` wants the clip to hide
a non-focused grid; the owner's rule wants it to keep a travelling card. Both cannot hold while the
clip is the isolation mechanism, and the owner has ruled isolation is the CAMERA's job. **The
resolution this points at: the board's clip window spans every grid, the camera frames one, and
`TP-141` is re-read against the CAMERA rather than the board window** — the same substitution
`TP-140` already makes. Not built, and it is a rewording of a planned row, so it is the owner's.

## RE-DERIVED AGAINST THE SCALED RESERVE — MEASURED, 3 grids, in the wall

`GAP-038`=(b) scaled the HUD, so the reserve is **521.7**, not 402. Measured pose, focused on the
middle grid:

```
design 1495 x 841        camera shows x [14.66 .. 1480.34]        board_zoom 1.649
grid 1 cell block x 830.25 .. 1186.44,  centre 1008.35
  == 521.7 + (1495 - 521.7)/2 exactly -- the post-HUD centring is correct
grid pitch = z x (block 216 + buffer 211.75) = 705.36
  grid 0 spans  124.90 .. 481.08     camera edge 14.66   -> INTRUDES BY 466.4 px
  grid 2 spans 1535.62 .. 1891.80    camera edge 1480.34 -> already out
```

⚠ **ONLY THE LEFT NEIGHBOUR INTRUDES, AND THE HUD IS WHY.** The reserve shifts the board right by
half of itself (260.85), so the right neighbour is pushed clear for free while the left one is
pulled in by the same amount. The buffer is ONE number by contract, so closing the left side pays
for the right side too.

```
isolation needs  z x (buffer + 108) >= 1008.35 - 14.66 = 993.69
at z = 1.649     buffer >= 494.6      (today 211.75)
W = 3B + 4 x buffer  ->  W ~= 2626, H ~= 1477     (first iteration; z moves with W)
```

- `game_picture_max_render_px` is 4096, so **`TP-114` is safe** and the render target is not the
  problem.
- ⚠ **SHARPNESS IS NOT THE PROBLEM EITHER** — a picture larger than the window is MINIFIED, and
  minification is safe (only magnification costs sharpness). The earlier note in this gap worrying
  about sharpness was wrong.
- ⚠ **THE REAL COST IS THAT THE FOCUSED GRID GETS SMALLER ON SCREEN.** The buffer grows faster than
  the block, so the grid's share of the picture's width falls, and the camera fits the whole picture
  into the window. Growing the picture to isolate a neighbour shrinks the thing the player is
  looking at.

## ⚠ `_isolates_at_buffer()` NOW MODELS A ZOOM THE BOARD DOES NOT USE

It solves at `picture.y / (block.y + strip)`. The real `focused_board_zoom()` is
`min(height fit, width fit)` over a denominator that now also carries the panel gutter, the two
card-row buffers and the scroller band, and the width fit subtracts the HUD reserve. **The derived
buffer is therefore solving the wrong equation** — which is why the shipped 211.75 no longer
isolates anything. Whatever this gap is answered with, that function has to be re-pointed at the
real zoom, or deleted along with the buffer being derived at all.
