# GAP-043 — effects cannot feed the combo without a reset rule, and the grid game has none

status: ANSWERED — combo never resets and is deliberately unbounded. What remains is
        IMPLEMENTATION: which condition replaces `_act_cancellable` at `game.gd:231`.
raised: the second closing phase, reviewing the ~272 commits the first close had skipped
design: `DESIGN.md` D11 (`Q323`=b), D13; `PLAN.md` §S14, §1.6
severity: LIVE — every show is scored with a smaller multiplier than D11 specifies

## THE DEFECT, WHICH IS NOT IN DOUBT

`Levels/game.gd:231` — `if feeds_combo and _act_cancellable: register_combo(mod.combo_key(function))`.

`_act_cancellable` is written in exactly two places, `game.gd:452` and `:455`, both inside
`_perform_next()`, bracketing the `on_next` window. **`place_card_in_grid` never sets it**, and a
placement is the grid game's only scoring action. `CardEnvironment.run_all_mods` is the only dispatch
passing `feeds_combo = true` (`card_environment.gd:113,120`), and the placement cascade calls it four
times: `on_board_mutated` (`game.gd:689`), `on_card_placed` (`:770`), `on_score` (`:1145`),
`on_after_score` (`:1146`). The base `CardModifier.combo_key` returns a non-empty script path, so
those mods would register if the gate let them.

`DESIGN.md` D11 is *"melds and effects both feed combo on the same terms"*. **They do not.** Only the
meld class (`game.gd:989`) and three effects that self-register at their own seam
(`prop_score_props.gd:16`, `prop_score_talents.gd:16`, `status_juggling.gd:80`) reach the multiplier.

⚠ **THOSE THREE CARRY A STALE COMMENT** — *"also reaches the dispatch hook via run_all_mods;
register_combo is idempotent, so the double registration is harmless."* On the placement path the
dispatch hook does not reach it, so those self-registrations are LOAD-BEARING.

⚠ **ORIGIN `b36c5336`, PRE-GRID.** `_act_cancellable` meant "an act is resolving" when the act WAS
the `on_next` cycle. The scoring action moved to placement; the flag did not.

## ⚠ WHY THE OBVIOUS FIX IS WRONG, AND WHY THIS IS A GAP RATHER THAN A DEFECT

Deleting the gate looks like a one-line fix. **It would break scoring outright**, because the grid
game has no combo reset at all:

- **`combo_repeats` is NEVER cleared. Anywhere.** Grep every production write: `game.gd:210`
  (`+= 1`) is the only one. Nothing zeroes it.
- **`combo_classes` is cleared in exactly one place — `GameData.apply_act_score():94` — which is DEAD
  PRODUCTION CODE.** Its only callers are tests (see the handoff's Open bugs). So in the shipped grid
  game nothing clears it either.
- **The multiplier is uncapped.** `combo_mult() = 1.0 + combo_unique_step * classes +
  combo_repeat_step * repeats`, and `player_settings.gd` ships `combo_unique_step = 1.0`,
  `combo_repeat_step = 0.5`, `combo_cap = 0.0` — and `combo_cap` of 0 means NO CAP
  (`game_data.gd:80`).

So the gate is currently **the only thing bounding combo growth from mod dispatch**. Open it and every
mod firing on every placement adds a class or a repeat, at +0.5 each, for the length of a show, with
no ceiling. `live_total() = board_total() * combo_mult()`, so the score would run away.

**D11 therefore cannot be delivered by removing the gate. It needs a reset rule, and D13 —
*"HUD is always live: no act, no banking moment"* — deliberately removed the event that used to
provide one.** That is a decision the design does not cover: two or more defensible answers, observably
different, expensive to reverse once content is tuned against it. Hence a gap, not a defect.

## ⚠ THE OWNER'S RULING — THE RESET HALF IS SETTLED

Owner, verbatim:

> *"as for combo resetting, i dont expect combo to reset anymore due to removal of acts."*

**So combo NEVER resets. It accumulates for the whole show.** That eliminates options (a), (b) and
(d) below — all three reset on some boundary — and selects the shape of (c), *without* yet answering
(c)'s cap.

### ⚠ WHAT THAT MAKES SHARP, AND IT IS NARROWER THAN THE FOUR OPTIONS

`combo_mult() = 1.0 + combo_unique_step * combo_classes.size() + combo_repeat_step * combo_repeats`.
**The two terms behave completely differently under a no-reset rule, and only one of them is a
problem:**

- **The CLASS term is naturally bounded.** `combo_classes` is a SET keyed on each modifier's script
  path, so it saturates at the number of DISTINCT modifier scripts the deck can fire — a content
  number, in the dozens. A show that runs long stops adding classes because it has already seen them
  all. At `combo_unique_step` 1.0 that is a bounded, designed reward for variety.
- **The REPEAT term has no bound at all.** `combo_repeats` increments on EVERY re-registration of an
  already-seen key (`game.gd:210`), and nothing anywhere clears it. Under acts it counted repeats
  WITHIN ONE ACT — a small number by construction. **Without acts it counts every repeat in the
  show.** Open the gate for D11 and every mod firing on every placement adds `combo_repeat_step`
  (0.5), for as long as the show lasts.

**So the reset ruling does not by itself make D11 safe — the class term it makes safe, the repeat
term it makes unbounded.** The remaining decision is only about repeats.

## ⚠ THE SECOND RULING — UNBOUNDED IS THE DESIGN

Owner, verbatim: *"unbounded by design"*, answering the three shapes below.

**So shape (iii) is chosen: repeats keep counting, uncapped, for the whole show.** No cap, no reset,
no change to `combo_repeat_step`. `combo_mult()` grows for as long as a show runs, and the goal curve
is what has to meet it — which ties this to `GAP-041`, still open on that curve's growth term.

**THE DESIGN QUESTION IS CLOSED. ONE IMPLEMENTATION QUESTION IS NOT.**

`game.gd:231` currently reads `if feeds_combo and _act_cancellable:`. Something must replace
`_act_cancellable`, and the choice is not free:

- ⚠ **DO NOT simply delete the condition.** `_note_mod_fired` fires on EVERY dispatch, and
  `run_all_mods(&"on_game_start")` (`game.gd:264`) runs before the player has acted. Rules cards
  return `""` from `combo_key` and so opt out, but any content mod with the default key would
  register a combo class during SETUP.
- ⚠ **DO NOT gate on `processing` either, even though it works.** `_broadcast_board_mutation`
  (`:687-690`) sets it true across the whole scoring cascade — `on_board_mutated` → the detector →
  `score_line` → `on_score` — and it is false at `on_game_start`, so it would deliver D11 on the
  scoring path. **But `processing` is the INPUT LOCK.** Gating combo on it repeats exactly the
  mistake that caused this defect: `_act_cancellable` meant "undo may cancel this act" and was
  pressed into service as a combo gate, and the meaning drifted out from under it the moment the
  scoring action moved. A second overloaded flag would be the same bug with a new name.
- ✅ **The honest fix is an explicit flag that means what it says** — an act is open — set in
  `_begin_act()` and cleared where each act ends. `_begin_act()` is already the one place an act
  starts (`place_card_in_grid:742` for a player placement, `_perform_next:450` for `on_next`), so
  the set site exists; the clear sites are what the implementer must find and name.
  ⚠ Note `on_card_placed` (`:770`) fires OUTSIDE `_broadcast_board_mutation`'s window, so a
  `processing` gate would miss it while an act-open flag would not — another reason the two are not
  interchangeable.

⚠ **THE THREE SHAPES BELOW ARE ANSWERED AND KEPT ONLY FOR THE RECORD.**

## WHAT WAS OPEN — one question, three shapes (ANSWERED: iii)

Given combo never resets, and given D11 requires effects to feed it:

**(i) Repeats stop counting.** `combo_repeat_step` → 0, or the repeat branch stops incrementing.
Combo becomes purely "how many DISTINCT things fired this show", which is bounded by content and
needs no cap. Simplest, and it keeps the multiplier meaning one legible thing.
⚠ It retires a shipped knob and `TP-58`, which tests it — and which has ZERO references in `Tests/`
today, so nothing would go red either way.

**(ii) Repeats keep counting, `combo_cap` gets a value.** Preserves the current shape and bounds it.
⚠ The cap is new tuning that interacts with the goal curve, which `GAP-041` already has open.

**(iii) Repeats keep counting, uncapped, and that IS the design** — a show-long escalating
multiplier. Defensible only if the goal curve is meant to escalate with it; `GAP-041` says the
growth term currently has the wrong sign for most of a run, so these two must be answered together.

⚠ **THE ORIGINAL FOUR OPTIONS BELOW ARE SUPERSEDED** by the ruling above and are kept only so the
reasoning that led here is not lost.

## OPTIONS (SUPERSEDED — kept for the record)

**(a) Leave the gate. Amend D11 instead.** Effects feed combo only in the `on_next` window; melds feed
it on placement. Costs nothing, changes no balance, and makes the code honest — but it abandons a
ruling the owner already gave, and the three self-registering effects stay inconsistent with every
other effect.

**(b) Open the gate; reset combo per PLACEMENT.** Each placement becomes the combo window, replacing
the retired act. Big single-placement multipliers, back to x1 each time. Closest to the pre-grid feel.

**(c) Open the gate; combo accumulates for the whole SHOW, with `combo_cap` set.** The multiplier
becomes an escalating reward for a long show, bounded by the cap. Fits D13's "no banking moment"
most naturally, but the cap value is new tuning and the curve interacts with `GAP-041`.

**(d) Open the gate; reset per MELD.** `_begin_meld()` (`game.gd:145`) already exists and already
brackets exactly one scored line, so the machinery is there. One placement completing a row, a column
and two diagonals would score four independent combos.

⚠ **CHECK FOR A FIFTH OPTION FIRST.** Six gaps in this stream were answered with an option nobody
listed. The real question underneath is *what is the unit the combo measures* now that the act is
gone — and the owner may name a unit none of these four assume.

## WHAT MUST NOT HAPPEN

Do not open the gate without answering the REPEAT question in the same change. The reset question is
answered; the repeat term is the one that runs away. A run that ships (b),
(c) or (d) half-done produces an uncapped multiplier and every playtest number afterwards is garbage.
