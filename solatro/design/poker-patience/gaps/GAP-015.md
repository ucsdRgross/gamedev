# GAP-015 — `Q107` wants one score label per ROW, but a grid banks every row into ONE bucket

status: open
outcome: unresolved
raised: 2026-08-28, during execution plan step S24 (the score labels)
design: PLAN.md §1.7 (`Q124`, `Q125`); DESIGN.md `Q107`, `Q108`, `Q110`, `D22`; TEST_PLAN.md TP-91
severity: CONTRADICTION

## What the design says

`Q107`=(a) — *"Where do a grid's ROW score labels sit? · **(a)** to the left of the grid, **one per
row** — as today"*. `Q108` is settled the same way for columns, below the grid. `TP-91` restates it:
*"Row labels left; column labels below"*, one each.

§1.7 quotes the owner on storage: *"flat row and col scores, 2d arrays for row height and col height
scores, and single variable for special meld scores."*

## What the code does — measured

`Levels/game.gd::_add_grid_line_score` banks a scored ROW or COL into a bucket indexed by **GRID**,
never by which row or column scored:

```gdscript
var flat : Array[BigNumber] = state.scores_row if section.kind == ROW else state.scores_col
if section.height == 0:
    state.resize_grid_bucket(flat, g + 1)
    flat[g].plus_equals(amount)        # g is the GRID index. section.index is discarded.
else:
    state.resize_grid_levels(raised, g + 1, section.height + 1)
    (raised[g][section.height] as BigNumber).plus_equals(amount)
```

`GameData`'s own comment agrees: *"`scores_row`/`scores_col` hold the height-0 (flat) bucket **per
grid**; `scores_row_h`/`scores_col_h` hold the raised-level buckets, indexed `[grid][height]`."*
`_row_term(grid)` then sums that grid's flat bucket plus every raised one.

So **there is no per-row-index number to put in a per-row label.** Five row labels on a 5x5 grid
could only show the same figure five times, or four zeroes and one total.

⚠ This is not a rendering gap. The information does not exist in the state.

## Why the two readings are both defensible

§1.7's quote reads either way. *"flat row and col scores"* can mean a flat array **indexed by row**
(one score per row, which is what `Q107` then places), or a **flat, i.e. height-0** bucket per grid
(which is what `S12` built, and what `_row_term` needs to multiply). The `2d arrays for row height
and col height` half is `[index][height]` under the first reading and `[grid][height]` under the
second — and `S12` chose the second consistently, including in the save format.

## What it blocks

`S24` entirely: `TP-91` (row labels left, column labels below) and `TP-94` (a label animates on
change) cannot be written against storage that has no per-row value. `TP-92` (height labels) and
`TP-93` (no subtotals) are unaffected — `scores_cell` IS per cell, and `D22` is a negative claim.

## Options I can see

- **(a)** The STORAGE is wrong: `scores_row`/`scores_col` become per-row/per-column arrays within a
  grid (and the raised ones `[index][height]`), `_row_term` sums them for the product, and the
  labels read one entry each. Faithful to `Q107` as written · costs a migration of the save format
  (`packed_grid_row_*`, `packed_grid_row_h_lens`) and of `S12`'s tests.
- **(b)** The LABELS are wrong: one row label and one column label per GRID, not per row — the
  three buckets are what the player needs to see, and `Q107`'s *"one per row"* was written before
  the three-bucket economy settled. Cheapest, and matches the code · but it contradicts `Q107` and
  `TP-91` verbatim, and leaves a 5x5 grid with two numbers beside it.
- **(c)** Per-row labels that display a DERIVED number — each row shows what that row has
  contributed, tracked in a display-only accumulator alongside the buckets. Keeps both the economy
  and the labels as written · a second source of truth for the same money, which is the shape that
  drifts.
- *my recommendation* **(a)**, because `Q107`, `Q108` and `TP-91` all state per-row placement
  independently and a per-grid bucket is recoverable from per-row entries by summing, while the
  reverse is not — but it is the only option that touches the save format, and `S12`'s
  round-trip tests go with it.
