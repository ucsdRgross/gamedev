# GAP-031 — the overview frames ONE grid BY CONSTRUCTION, so `GAP-027`'s (e) is provably a no-op

status: resolved
outcome: answered by the owner — **(d) NEW, none of the listed options**: the main container is
  3 GRIDS wide, each grid its own container centred on its centre cell; the camera KEEPS a step
  inside the 3

## OWNER ANSWER — (d), a fourth option nobody listed

> *"the main container should be 3 grid wide by default. Each grid is its own container centered on
> the center cell of each grid. This way zooming out shows all 3 grids, and there is no horizontal
> scroller needed until more than 3 grids exists"*

**This dissolves the contradiction at its root rather than trading one chart node for another.** The
~1000 px of empty board between neighbours was never a `grid_buffer_px` problem: the canvas was
**3 POSITIONS of 3 grids each — nine grids of width — to hold three grids.** Collapsing it to three
grids removes the position/picture indirection entirely.

```
was    one position = (3*216 + 2*buffer) * 1.12 = 1219      picture = 3 positions = 3656
now    the picture IS 3 grids wide              = ~923 at buffer 88
```

### The camera keeps its step — ruled explicitly

The owner chose **"keep a step inside the 3"** over retiring it: the picture is 3 grids wide, the
camera still RESTS ON ONE GRID and steps between the three, and **zooming out is what shows all
three at once.** So `H22` and `H9` stay literally intact and `GAP-024`=(b)'s stepping stays
meaningful at 3 grids.

⚠ **The two modes now differ by MECHANISM, not only by content scale** — the overview frames the
whole picture, the focused view frames one grid. That is `GAP-027`=(d)'s "the overview's zoom is not
the position-fills-frame zoom", reached by a different route. **`GAP-027` and its 128 px floor are
superseded by this ruling; do not build the floor.**

⚠ **`GAP-021` (one grid per position) is undone by this.** Grids are no longer spread one per
1219 px position.

⚠ **No horizontal scroller until a 4th grid exists** — which is where `GAP-028`=(c) lives.

### ⚠ OPEN AND DELIBERATELY DEFERRED — render sharpness, to be settled BY EYE

A ~923 px canvas against a 1152 px window means the wall camera **MAGNIFIES** the SubViewport
texture ~1.25x at rest, where today's resting view MINIFIES at zoom 0.96 and is sharp.
`GAP-024`=(b) was answered precisely because magnifying that fixed texture softens card art.
Readability is NOT the concern (a 216 px grid renders at ~270 px, larger than today) — sharpness is.

**The owner ruled: MEASURE FIRST.** Build the change, render it, and compare actual pixels against
today's view before choosing a sharpness strategy. ⚠ The candidate fix — authoring the canvas at a
higher pixel density so the texture is window-width before the camera touches it — must be measured
against the render clamp, which was observed to BITE at 6096 -> 4096.

⚠ **The instrument must render the PRODUCT's framing.** `grid_zoom_shot` and `grid_layer_shot`
instantiate `GameView` DIRECTLY and are blind to the whole wall composite — that blindness is why a
squash defect passed two by-eye gates. Use the shape `wall_game_squash_probe` uses, which builds its
`PictureEntry` from `Wall.load_layout()`.

## ⚠⚠ THE PREMISE THAT WAS WRONG

`HANDOFF` and `GAP-027` both state: *"`focused_scale()` PICKS ITS ZOOM FROM THE PICTURE'S HEIGHT, so
the camera's visible WIDTH is ~1218 px however wide the picture is. No width change widens the
view."* The 128 px readability floor was derived from that sentence.

**It is only true while the picture's WIDTH is fixed. It is not.** `grid_position_size_px()` ends:

```gdscript
var aspect_minimum := width * ref_h / ref_w
return Vector2(width, maxf(block.y, aspect_minimum))
```

**The height is DERIVED FROM THE WIDTH.** So narrowing the picture shortens it, the height-keyed
zoom rises, and the visible width shrinks by the SAME factor. Everything scales together.

## The measurement

`S45` scaled the buffer by `card_scale` (220 -> 88), and both quantities moved by one ratio:

```
pitch (one grid position)   1218.6 -> 922.9      x0.7573
camera visible width        ~1194  ->  904.58    x0.7576
frame / pitch                0.98  ->   0.98     UNCHANGED
```

The observed `TP-105` rect, which is what exposed it:
```
visible  x [470.6 .. 1375.2]   y [-909.9 .. -401.1]
grid     x [818.5 .. 1034.5]   y [-666.0 .. -380.0]
```
⚠ Note it fails on **Y**, not X — the grid hangs 21.1 px below the frame. The first reading of this
failure attributed it to `GAP-027`'s WIDTH residual; **the numbers say otherwise**, and that
misattribution is what this gap exists to stop being repeated.

## ⚠ THE PROOF THAT NO BUFFER VALUE CAN HELP

With `grid_max_count` = 3 and the reference window 1152x648 (ratio 0.5625 — `viewport_width` /
`viewport_height` are not overridden, so Godot's defaults apply):

```
smallest possible span  (buffer 0) = 3 * block.x = 3 * 216      = 648
smallest possible width            = 648 * 1.12                 = 725.8
its aspect_minimum                 = 725.8 * 0.5625             = 408.2
block.y                                                          = 286
408.2 > 286  ->  the aspect minimum DOMINATES at every buffer value, including 0
```

So the position is **always exactly window-aspect-shaped**, and a camera that fills the window
frames **exactly one position, by construction, for every possible `grid_buffer_px`.**

⚠ **The code says this is DELIBERATE**, in `grid_position_size_px()`'s own doc comment: *"The camera
rests by OVERFILLING the window, so a picture whose own aspect is the window's is framed WHOLE at
rest and the camera has nowhere to step — measured, at every width. Sizing the POSITION to the
window aspect and the picture to `grid_max_count` of them is what leaves the camera a step."*

**`H22`'s camera step and `H5`'s multi-grid overview are in direct conflict**, and the position/window
aspect coupling is the mechanism. `H5` cannot be satisfied by any buffer, margin or pitch change.

## Options

- **(a) The overview's zoom stops being the position-fills-frame zoom.** Give the OVERVIEW its own
  zoom, keyed to the readability floor, and let it frame several positions; the FOCUSED mode keeps
  the current position-fills-frame rule. This is `GAP-027`=(d) with the mechanism corrected — the
  floor is real, but it must drive a zoom that is NOT derived from the position aspect. ⚠ Costs:
  `H22`'s "camera steps between positions" must be re-read, since a zoomed-out overview spans
  several at once, and `TP-105`/`TP-140` re-point again.
- **(b) Accept the one-grid overview and change the DESIGN.** `H5` and `H6` are struck; the two modes
  differ by content scale and the camera step is the only navigation. Cheapest, honest, and it is
  what every measurement so far says the architecture actually builds.
- **(c) Decouple the position from the window aspect** — size the position to its CONTENT and let
  the picture be as wide as it needs. ⚠ The comment above records this was tried: a picture whose
  aspect is the window's *"is framed WHOLE at rest and the camera has nowhere to step — measured, at
  every width."* Reopening it means giving up `H22`'s step, so it trades one chart node for another.
