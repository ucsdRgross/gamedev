## ⚠ ESCALATED — this is no longer a question of TIMING

Phase 6's by-eye gate rendered the board at 1, 2 and 3 grids and **the 3-grid case is wrong on
screen**. Measured by the overseer's own run of `Tests/Visual/grid_layer_shot.tscn`:

```
n=3 window x [423.0 .. 1134.0] centre 778.5
n=3 container x 427.0 w 731.0 (min 731.0), scroll 0.0/731.0, bar visible true
n=3 grid 0 panel centre  547.5 (-231.0), cells [447.0 .. 663.0], off-screen  0.0
n=3 grid 1 panel centre  792.5 ( +14.0), cells [692.0 .. 908.0], off-screen  0.0
n=3 grid 2 panel centre 1037.5 (+259.0), cells [937.0 .. 1153.0], off-screen 19.0  <-- CUT OFF
```

Two facts settle it:

1. **The board does not fit, and cannot.** Minimum content width at 3 grids is **731 px** against
   **703 px** of usable viewport. Even the cells alone span 706. ⚠ An earlier reading of this as
   "the board fits and is clipped anyway" was WRONG — it compared against the container's OUTER
   rect (711), which includes scroll chrome. There is **no** scroll position at 3 grids that shows
   everything.
2. **Nothing positions the board horizontally at open** — it rests at `scroll_horizontal = 0`, hard
   left, while `pan_grid` claims the view is centred on grid 0. `G10`'s 778.5 would need
   `scroll = 14`.

**Why the absent knob causes it.** `Q35`=(b) fixes that grids are spaced by their **CELL blocks**
with the labels sitting **in the buffer between them**. Today there is no buffer: grids are spaced
**panel-to-panel at `separation = 4`**, so each panel's 25 px of label gutters is **added to the
board width instead of being absorbed by a buffer**. That is the 75 px turning a 706 px cell span
into a 731 px board — the near-fit regime is an artefact of the missing knob. With
`grid_buffer_px` = 220 the cell pitch is 436 and three grids span 1308 px: the board overflows
decisively, panning is unambiguously the answer, and `G10` reads as a board-space statement.

⚠ **`TP-101` ("every pan lands a grid centred; no cut-off grid at rest") did not catch this**
because it CALLS `pa.pan_to_grid(0)` before measuring — which is exactly the call the resting board
never makes. The test sets up the very condition whose absence is the bug.

⚠ **OVERSEER CORRECTION — the premise below was wrong on one point.** This gap as filed said
`Q35` is unanswered. **`Q35` = (b), answered 2026-08-28**: *"no — grids are spaced by their CELL
blocks and the labels sit in the buffer between them."* So `grid_buffer_px` does **not** have "two
different meanings on screen" — its meaning is fixed: the gap is measured between CELL BLOCKS and
the score labels live inside it. Option (b) below loses its stated blocker; what remains of the
decision is only WHEN the knob lands and whether the re-measurement is worth doing in Phase 6.

## The situation

`NAMES.md` §6 says both knobs are **registered but absent from code, and they are `S28`'s**. After
`GAP-016`=(d) cut `S28` down to `TP-104` and `TP-106`, neither test needs either knob, and neither
has an obvious call site in Phase 6:

- **`grid_buffer_px` (220.0)** — "the gap BETWEEN grids". The gap today is `GridContainer`'s scene
  `separation = 4`. Making it the knob is a real visual change to every board, and `grid-view`
  `DESIGN.md` `Q35`=(b) fixes what it measures: **between CELL blocks, with the labels sitting in
  the buffer.** So the meaning is settled; only the timing is open.
- **`grid_overview_margin` (0.06)** — "fraction of margin around the all-grids view". The all-grids
  framing is the CAMERA's, and `GAP-016`=(d) moved the camera to Phase 7 with `S31`.

`S28` therefore introduced neither, rather than landing a visual change to every board inside a
step whose done-when does not mention one.

## Options — ESCALATED SET (these supersede the timing options below)

⚠ **`G10` "3 put the middle where a single grid sits" and `Q150`(a)/`H9` "no viewing a cutoff grid"
are NOT simultaneously satisfiable at the current measurements.** That is the decision.

- **(i)** — **Land `grid_buffer_px` as the CELL-BLOCK-to-cell-block gap, per `Q35`(b).** Three grids
  then span 1308 px and never fit, so the resting position is `pan_to_grid(pan_grid)` and `G10` is a
  BOARD-SPACE statement, not a screen one. Fixes the root cause; changes every multi-grid board's
  spacing; `TP-101`/`TP-106` need re-measuring.
- **(ii)** — **Keep the 4 px gap; make the rest position the CONTENT CENTRE.** `G10` becomes exact on
  screen (middle grid at 778.5) at the price of ~5 px of grid 2's cells clipped. Smallest change,
  keeps the near-fit regime and its fragility.
- **(iii)** — **Keep the 4 px gap; rest on `pan_to_grid(0)`.** The clamp drives the board hard right:
  grid 0 clipped ~4 px, grid 2 whole. Satisfies "no cut-off grid" for the grid you are on, breaks
  `G10` on screen.

## Options — the ORIGINAL timing set, kept for the record

- **(a)** — Both knobs land in Phase 7 with `S31`: the wide picture is what sizes the grid
  positions, so the gap and the overview margin are both framing decisions made there.
- **(b)** — `grid_buffer_px` lands now as `GridContainer`'s separation — `Q35`=(b) already fixes
  what it measures, so this needs only re-measurement of every "no cut-off grid at rest" check —
  and `grid_overview_margin` waits for the camera.
- **(c)** — Retire `grid_overview_margin` if the camera's own framing supersedes a margin fraction,
  and keep only `grid_buffer_px`.

## What observably differs

(b) widens every multi-grid board by ~216 px per gap, which changes how many grids fit the window —
the exact quantity `TP-106` measures. (a) and (c) leave Phase 6 geometry as shipped.
