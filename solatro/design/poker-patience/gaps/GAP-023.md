# GAP-023 — nothing says how the board's `pan_grid` reaches the wall's camera

status: resolved
outcome: answered — (e), a CONTINUOUS pan offset crosses the boundary; the criterion is touch-drag feel
raised: scoping execution step `TP-105`/`H22` (the camera steps between grid positions)
design: DESIGN.md §36 flowchart H (`H11`, `H22`, `H23`), `QR3`, `Q160`, `GAP-016`, `GAP-022`
severity: MISSING DECISION

## OWNER ANSWER — judged by TOUCH-DRAG FEEL, which rules out every option as posed

Verbatim: *"whichever version is best for potentially moving view based on touchscreen dragging.
Ideally horizontal scrollbar is hidden so it feels natural whether grid movement is camera based or
scroll based and player doesnt really feel the difference between the two"*

⚠ **THIS IS A FIFTH OPTION, AND IT INVALIDATES THE FOUR AS WRITTEN.** All of (a)-(d) carry a
DISCRETE GRID INDEX across the boundary, and an index can only ever step. A finger drag must track
the finger continuously.

**(e) A CONTINUOUS PAN OFFSET crosses the boundary; a grid step is just a target value of it.**

- The camera's pose is `resting_state()` plus a continuous horizontal offset in pixels.
- **Grid stepping** = animate that offset to `n * grid_position_size_px().x`.
- **Touch drag** = set that offset from the finger delta, live.
- Because both are the SAME mechanism, they cannot feel different — which is the owner's whole
  criterion. Under any index-carrying option they are two mechanisms and the seam is felt.
- The camera's pose stays written by WALL code, which is what `H11` ("Camera2D limit and smoothing
  do the clamping") asks for. Only one continuous number crosses.

⚠ **THE HORIZONTAL SCROLLBAR MUST BE HIDDEN.** Owner's words. A visible bar advertises which
mechanism is moving the view and destroys the equivalence. The scroller's VERTICAL axis keeps its
`H13` job (tall stacks, oversized grids) and its bar is not covered by this.

⚠ **`H17` STILL DISCRIMINATES**: *a drag that STARTS on a card is a placement; a drag that starts on
empty board is a pan* (`Q192`=a). This answer changes what a pan DOES, not what counts as one.
⚠ **`H10`'s edge bounce and `H9`'s "always landing centred" now belong to the offset**, not to the
scroller. `_bounce_board()` is a re-point target, not a thing to leave behind.

## What was found

`H22` requires the wall camera to step between grid positions. Measured, current tree:

- `PlayArea.pan_grid` — the index of the grid the view is on — lives **inside** the game picture's
  `SubViewport`, under `screen_root`.
- The `Camera2D` that frames the picture is a **`Wall`-level `%Camera2D`, outside that viewport.**
- **No signal path between them exists.** `WallPicture.resting_state()` is a pure function of
  `rect` / `window_size` / settings and never reads `pan_grid`; the only camera-pose writers are
  `Wall.pan_by()` / `clamp_pan()` and `WallTransition._apply()`.

So the design says the camera steps, and every panning site that knows WHICH grid to step to is on
the far side of a viewport boundary from the camera that must move. **No answered node fixes how the
one reaches the other.**

⚠ **`GAP-022`=(a) raised the stakes.** "Out of view" now resolves against the CAMERA's rect, so this
is no longer only about motion — every out-of-view claim on the board depends on this wiring.

## Why this is a gap and not a defect

More than one option is defensible, they differ in coupling and in observable smoothness, and the
choice is expensive to reverse: it fixes the direction of dependency between the board and the wall,
and `TP-101`, `TP-103`, `TP-105`, `TP-106`, `TP-112`, `TP-138`-`TP-141` all have to be re-pointed at
whatever it produces. ⚠ **`NAMES.md` also has no entry for a camera-pose-per-grid function**, so the
name is being coined here and should be fixed once.

## Options

- **(a) `PlayArea` emits; `Wall` listens.** A signal carrying the wanted grid index crosses the
  boundary and the wall moves its own camera. Keeps the camera's pose written only by wall code,
  which matches `H11` putting limit and smoothing on the camera. Costs a new signal and a
  subscription that must survive rebuilds — ⚠ `setup_gui()` is also the undo-rebuild path.
- **(b) `Wall` reads `PlayArea.pan_grid` each frame.** The same shape the HUD now uses
  (`pan_grid * grid_position_size_px().x`), and it needs no signal. Costs the wall reaching INTO the
  picture's contents every frame, which inverts the dependency the rest of the wall keeps.
- **(c) The pose is a pure function and the CALLER supplies `n`.** `WallPicture` gains
  `camera_state_for_grid(n)` beside `resting_state()`, and whoever already knows `n` calls it — no
  new coupling in either direction, and the wiring question narrows to "who calls it". This is the
  slice being built first because it is true under (a) and (b) alike.
- **(d) The board keeps owning the pan and the camera MIRRORS it.** The scroller's horizontal aim
  (now ~16 px of dead range) is replaced by a camera write issued from the same site that already
  computes the aim — `pan_to_grid()`. One writer, at the site that already exists, and every
  existing caller keeps working. ⚠ Costs the board writing a wall-owned node, which is exactly the
  boundary `GAP-022` and the card-effect API gate exist to protect elsewhere.

## Meanwhile

observable is a shape this stream has been burned by repeatedly — most recently the furniture
origin, where the fix was to delete the second mechanism rather than reconcile it.
⚠ **`TP-141` must RE-EARN its painted-pixel evidence** (`100,908 px red, 0 px green`) against the
camera boundary. It counts pixels precisely because a position-based assertion passed both before
and after the defect it proved; re-pointing it without re-running that measurement would silently
downgrade the strongest check here.
⚠ **The scroller is NOT redundant.** `H13`/`H23` give it tall stacks and revealing more of a single
oversized grid — its vertical axis keeps doing real work. Only its horizontal axis goes quiet.
