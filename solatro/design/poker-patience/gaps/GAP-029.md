# GAP-029 — `grid_buffer_px`'s 220 is stated at `card_scale` 2.5 while the game ships at 1.0

status: resolved — SUPERSEDED BY A SECOND OWNER RULING
outcome: answered by the owner — **DERIVE the buffer from the isolation rule**, not from a literal
  and not from `card_scale`

## ⚠⚠ THE FIRST ANSWER WAS WITHDRAWN — `220` IS LOAD-BEARING, NOT A STALE 2.5x ARTIFACT

The original ruling (scale by `card_scale`, shipping `220 / 2.5 = 88`) rested on a DOCUMENTATION
argument: that §1i's table, stated at `card_scale` 2.5, meant the raw 220 was 2.5x too large.
**The geometry contradicts it.** At buffer 88, focusing leaves ~194 px of EACH neighbouring grid
bleeding into the window, so `H6` (*"clicking a grid zooms in on it"*) stops isolating a grid and
`TP-140` (*"grid 0 / grid 2 is OUT OF VIEW while another grid is focused"*) fails on both sides.

**The buffer's real job is to separate grids enough that focusing isolates one.** Nobody had measured
what the number DOES before ruling on what it MEANS.

## OWNER ANSWER — register the RULE, not the number

> *"Set the buffer from the rule"* — derive `grid_buffer_px` from the requirement that a focused grid
> isolates its neighbours, so the buffer is whatever the focused zoom and window demand, and stays
> correct if either changes.

⚠ **DERIVE IT FROM MEASURED QUANTITIES, NOT FROM ANY NUMBER IN THIS FILE OR THE HANDOFF.** An earlier
estimate of "buffer >= 214.2" DOES NOT RECONCILE: the observed focused block width of 419.16 px
against a 216 px block implies a scale of 1.94, while the observed 467.67 px centre-to-centre pitch
implies only ~241 px unscaled, which would mean a buffer near 25. **Both cannot be true, so at least
one scale assumption behind that estimate is wrong.** The implementation must read the scale, the
block and the camera's half-width from the LIVE scene and solve for the buffer there.

⚠ This is the second premise in this stream to fail the same way: a number reasoned from a formula
rather than read from the running product. **MEASURE, THEN DERIVE.**

## OWNER ANSWER — scale it by `card_scale`

The 220 in DESIGN.md §24 and NAMES.md is **authored at `card_scale` 2.5**, as §1i's table states.
The game ships at `card_scale` 1.0 and no code scales it, so the raw value in play is 2.5x what the
table describes. The buffer is scaled by `card_scale`, giving **88 raw px** against a 216 px cell
block. This makes the registered number mean what its own table says, rather than closing the
discrepancy by choosing a fresh literal.

⚠ The owner had twice declined to rule on this. It is now ruled.

## What was measured

`grid_buffer_px` is a LIVE term in `grid_position_size_px().x`:

```
span  = count*block + (count-1)*buffer
width = span * 1.12
buffer 220 -> (3*216 + 2*220) * 1.12 = 1218.6   -- reproduces the observed 1219 pitch exactly
buffer  88 -> (3*216 + 2* 88) * 1.12 =  922.9
```

So shrinking it DOES move grids closer: the pitch drops from 1219 to 923.

## ⚠ What it does NOT do

**It does not on its own dissolve `GAP-027`.** `focused_scale()` picks its zoom from the picture's
HEIGHT, so the camera's visible width stays ~1218 px however wide the picture is. At pitch 923 a
neighbour's cell block still spans to 1031 px against a 609 px half-width — out of frame. This is
why `GAP-027` was answered **(d) AND (e) together** rather than (e) alone.
