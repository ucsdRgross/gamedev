## OWNER ANSWER — (b), settings reach the code under test by injection

`use_own_settings()` and `restore_real_settings()` REASSIGN the global `SettingsManager.settings`;
`backup_real_settings()` alone does not. Under (b) the global stops being the channel: settings are
injected into the code under test instead, which removes the whole class of interference rather than
scheduling around it.

⚠ **This is the largest-blast-radius option of the three and the owner chose it knowingly.** Every
production reader of `SettingsManager.settings` is in scope.

## Why the alternatives were not taken

- **(a) every settings-touching suite joins the chain** — this is the shape that **DEADLOCKED
  TWICE** (`GRID LAYOUT` <-> `SETTINGS RANGE`, then <-> `GRID VIEW`, identical exclusion lists both
  times), each costing a 400 s timeout. ⚠ **DO NOT TRY A THIRD ORDERING SHAPE WITHOUT MAPPING THE
  WHOLE WAIT GRAPH.** The chain is `INTERACTION -> UI PROPS -> VISUAL LAYERS -> GRID VIEW ->
  SETTINGS RANGE -> E2E RUN -> LEAK CANARY -> WALL PAUSE`, each excluding everything after it.
  ⚠ The ordering chain only orders its own participants, so a non-participant is unordered against
  everyone and no chain position helps.
- **(c) snapshot values rather than swapping the object** — viable and cheaper, but leaves the global
  as the channel and so leaves the failure mode reachable.

## What it must fix, and how that is proved

Two of the five standing failures are owned by this:

```
GRID LAYOUT: ...the arithmetic lands on the same point the card's own CONTROL does -- worst 116.0 px out
GRID LAYOUT: TP-85: caught mid-growth, the row is PART WAY to its new height -- row 78.0, was 58.0, will be 78.0
```

⚠ **`GRID LAYOUT` ALONE IS `ALL 85 CHECKS PASSED`** with a 0.0 px delta at every height. The
failures exist only in the full suite. A constant `116.0` survived five wrong diagnoses before
isolation settled it: **deterministic interference reads exactly like a deterministic bug.**

⚠ **The poison CUTS BOTH WAYS — it causes two failures and MASKS two others.** So the done-when is
not merely "5 failures becomes 3": the full-suite result must be read for newly-REVEALED failures,
and a rise in the count may be the fix working.

## ⚠ `user://settings.tres`

The real settings file **is poisoned with test values and stays that way**; `isolated` suppresses
writes, so a poisoned file simply persists. A pristine default is recoverable from
`PlayerSettings.new()`. **Do not overwrite it without the owner.**

The three settings helpers and every call site, `Tests/UI/test_grid_layout.gd`,
`Tests/UI/test_settings_range.gd`, the `WALL FOCUS` suite, and every production reader of
