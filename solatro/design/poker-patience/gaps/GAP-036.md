# GAP-036 — the picture frame's edge margin is a FRACTION, not the inter-grid buffer

status: resolved
outcome: answered by the owner — **the edge margin equals the inter-grid buffer**; the picture gets
  wider to accommodate it
raised: owner instruction while the row-label work was landing
design: DESIGN.md §36 flowchart H (`H1`), `GAP-029` (the derived buffer), `GAP-031` (the 3-grid canvas)
severity: TWO GAPS THAT SHOULD LOOK THE SAME ARE COMPUTED DIFFERENTLY

## OWNER RULING

> *"grids should have same buffer against edge of picture frame as they do against each other, so
> picture frame may need to be wider."*

## What the code does today — measured

`PlayArea.grid_position_size_px()`:
```gdscript
var span  := count * block.x + (count - 1.0) * isolating_grid_buffer_px(settings_res)
var width := span * (1.0 + 2.0 * settings_res.grid_overview_margin)     # 0.06 per side
```

So **the gap BETWEEN grids is `isolating_grid_buffer_px()` (a derived pixel quantity), while the gap
at the picture's EDGE is `grid_overview_margin` — 6% of the span.** Two different quantities for two
gaps the player reads as the same thing, which is why they do not match.

## What it becomes

```
width = span + 2 * buffer      i.e.  3 * block.x + 4 * buffer  at grid_max_count 3
```

⚠ **`grid_overview_margin` then no longer drives the picture width.** Decide and record what becomes
of it: if it drives nothing else, it is a **dead registered setting** and must be removed —
`GAP-018` is exactly that failure mode and the owner has already ruled once (in `GAP-029`) to delete
rather than strand such a knob. **Check its other readers before removing it.**

## ⚠ It composes with the derived buffer for free — do not hand-derive it

`isolating_grid_buffer_px()` obtains its coefficients by **SAMPLING the real
`grid_position_size_px()` at two candidate buffers**, never by re-deriving its formula. So changing
the width expression is picked up by the solver automatically. **That is precisely why the sampling
design was chosen — do not replace it with a hand-derived formula here.**

⚠ But the solve is no longer the same shape: with `width = span + 2*buffer`, the buffer now appears
**four** times rather than twice, so the affine coefficients change. **Re-measure the solver's output
after the change and confirm it still returns a buffer that isolates a focused grid.**

## ⚠ Sequence: this belongs WITH the `TP-140` re-derivation, AFTER `GAP-035`

Three things all move the same geometry and must not be derived three separate times:
1. **`GAP-035`** moves the Entrance into the board's scroller, changing the focused-zoom formula.
2. **This gap** widens the picture, changing the camera's framing.
3. **The standing `TP-140` regression** (neighbours bleeding ~45 px into the focused view) is already
   owed a buffer-solver re-derivation.

**Do `GAP-035` first, then this and `TP-140` together as ONE geometry pass.** Deriving the solver
against a width that is about to change again is the mistake this ordering exists to prevent.
