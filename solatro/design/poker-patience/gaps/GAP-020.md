# GAP-020 — the saved pan has no camera to save it on, and the board already keeps it

status: open
outcome: —
raised: during execution plan step `S32` (`H18`/`H19`, the saved pan), after `S31b`/`S31c` landed
design: DESIGN.md §36 flowchart H (`H18`, `H19`, `H22`, `H23`), `Q171`, `Q172`, `Q173`, `Q179`;
`GAP-019` (resolved, (e) — "build the focused zoom first, then re-measure"; this IS that
re-measurement)
severity: A NODE WITH NOTHING TO IMPLEMENT

## The re-measurement `GAP-019` (e) demanded

`S31b`'s focused zoom is built and `S31c` clips the scroller. The zoom is the BOARD scroll
container's `scale`, INSIDE the picture — it did not change the picture, and
`PlayArea.game_picture_design_size` is untouched since `S31`. Measured now, via
`Tests/Visual/grid_zoom_shot.tscn` (the real picture) and a real `Main` in a 1152x648 viewport:

| fact | measured |
|---|---|
| game picture `design_size` | **1219 x 685** (unchanged by `S31b`) |
| board window inside the picture | **719 px** wide, unchanged |
| focused board zoom | **1.9406** — the focused grid fills the board window, neighbours clipped |
| camera resting pose on the game picture | position `(0, -738.5)`, zoom `0.9460` |
| picture width visible at that pose | **1217.8 of 1219 px — 99.9%** |
| camera slack before bare frame appears | **0.6 wall units, total, both edges** |
| on-screen grid pitch at the focused zoom | **~846 px** |

**The camera has 0.6 px to move where a grid step needs 846.** `H22`/`H23`'s camera stepping is
still not implementable, and neither is `H18`'s "the wall camera's resting pose becomes the SAVED
PAN": there is no second resting pose to shift to. `TP-105` stays parked and `TP-115` cannot be
written as specified.

## What a real leave-and-return actually does today — observed, not reasoned

A real `Main`: enter the show, focus grid 2, leave to `map`, re-enter via `Main.enter_game()`.

```
before leaving   focused_grid=2 pan_grid=2 scroll_h=750 board_zoom=1.9406 centred cells x=697.8
while away       focused_grid=2 pan_grid=2 scroll_h=750 board_zoom=1.9406 centred cells x=697.6
after returning  focused_grid=2 pan_grid=2 scroll_h=750 board_zoom=1.9406 centred cells x=697.6
```

Nothing is lost and nothing is restored, because nothing is torn down: `Main.enter_game()` RESUMES
an attached `GameView` ("focus alone, no rebuild"), and `WallPicture.unfocus()`/`focus()` change
only the render TARGET while `size_2d_override` holds the canvas at `design_size`, so the board
never re-lays out. The pixel check — the centred grid's on-screen x — moves 0.2 px across the round
trip.

Three consequences:

- `H19` ("leaving saves it; returning restores it") is already TRUE of the board's pan, by
  construction rather than by code.
- `Q172`=(a)'s "session state, resets on a restart" is already the observed behaviour: `_on_continue`
  restarts a resumed show fresh.
- `Q173`/`Q179`'s "snapped to the nearest grid centre" is FREE. The pan is `PlayArea.pan_grid`, a
  grid INDEX, and every path that can invalidate it already clamps it (`_recentre_board`,
  `_on_grid_removed`). A window resize never resizes the picture's canvas, so it cannot move the
  board at all.

## Why this is a decision, not a defect

`Q171`=(a) is a ⚑contract on a CAMERA function: *"the pose for the picture's SAVED pan offset — the
same shape, with the position shifted along the picture's width"*. On the shipped geometry there is
no shift to make. Reading `H18`'s "the wall camera's resting pose" as "the board scroller's resting
pan" is a DESIGN READING, not an inference an implementer may make silently — and under that reading
the whole node is already built.

## Options

- **(a) Close `H18`/`H19` as already satisfied by the scroller, and regression-test them there.**
  `resting_state()` is left exactly as it is. `TP-116` is written against `PlayArea.pan_grid` plus
  the centred grid's on-screen x across a real leave-and-return; `TP-115` and `TP-117` are rewritten
  or dropped, since neither has a camera pan to assert. Cheapest, changes no pixel, and matches what
  the product already does. Cost: `Q171`'s contract wording is left describing a pose the code never
  produces, and `H18` keeps saying "camera" while meaning "scroller".
- **(b) Resize the picture first — `GAP-019` (a) or (c) — then implement `H18` literally.** A
  picture several window-widths wide gives `resting_state()` a genuine pan offset, and `TP-105`,
  `TP-115` and `TP-117` all become writable as the test plan states them. Cost: everything
  `GAP-019`'s blast radius lists, and it is a Phase 7 re-opening of Phase 6 geometry.
- **(c) Park `S32` as `TP-105` is parked.** Implement nothing, assert nothing, and let `S33` proceed;
  revisit both together whenever `GAP-019` (a)/(c) is decided. Cost: the leave-and-return behaviour
  stays untested, so a future change to `enter_game()`'s resume path can silently break it.

## Blast radius

`S32` (blocked on this), `TP-115`, `TP-116`, `TP-117`, and `TP-105`, which is already parked on
`GAP-019`. `WallPicture.resting_state()` and its four call sites are untouched under (a) and (c).
Nothing else in Phase 7 depends on the answer.

## Meanwhile

**No product code was changed by `S32`** — the suite is where `S31c` left it. The two instrument
scripts written to take the measurements above were deleted after use.
