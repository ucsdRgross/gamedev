# GAP-001 — `step_x`'s signature cannot get the grid widths the contract needs
status: resolved
outcome: answered
raised: 2026-08-26, during execution plan step S1 (the BoardCoord type)
design: NAMES.md §1 (`BoardCoord.step_x(n)`); PLAN.md §1.1, §1.3
severity: CONTRADICTION

## OWNER ANSWER — a new option, none of the above

**Movement is by BOTH `x` and `y`, over one uniform virtual lattice.** Owner, verbatim:

> *"movement should be by both x and y. I don't know what grid widths is supposed to represent
> here, since theoretically grids are not guaranteed to be 5x5 if I decide to make it different
> shapes in the future, such as 6x6 or even a non square shape. If non square, it should treat
> empty spaces/zones as existing for sake of movement, but when it tries to land there is
> nothing there and it discards. If it moves outside of its grid and there is another grid
> there, then it can move onto that space. ignore gap between grids."*

The rule this produces:

- `step_x(n)` alone is **wrong** — the registry's single-axis method does not cover the
  behaviour. Movement takes a step in `x` **and** `y`.
- A grid occupies a **rectangular block of the lattice at its own bounding size**. Nothing is
  5x5; 6x6 and non-square are expected. A non-square or ragged grid's **holes still exist for
  movement** — a step may pass over and land on one.
- Grid blocks are **laid end to end with no lattice gap** between them. The visual
  `grid_buffer_px` is a rendering concern and does not affect movement.
- Stepping out of one grid into the next simply lands in that grid's block.
- **Landing resolves separately from moving.** A step always produces a coordinate; whether a
  cell exists there is asked at landing, and a landing on nothing discards (see GAP-002).

So per-grid bounding widths ARE the thing the arithmetic needs — that is what `grid_widths`
was reaching for, and the name did not say it. The registry's `step_x(n)` signature is
superseded by this answer rather than satisfied by it.


**What the design says** — `NAMES.md` §1 fixes the method's signature as
`BoardCoord.step_x(n)`, taking a single argument. `PLAN.md` §1.1 says `step_x` "crosses grid
boundaries; derives `grid` from the global column," and §1.3 says each grid carries its own
width, defaulting to 5, with nothing hard-coding 5 anywhere in the system.

**What the repo says** — `BoardCoord` is a bare `RefCounted` value type holding four ints
(`grid`, `x`, `y`, `h`) and nothing else. A value type with no reference to the grid list
cannot derive per-grid widths from `n` alone, so the shipped method is
`step_x(n, grid_widths: Array[int])` — a second parameter the registry does not name.

**What it does not say** — how `step_x` is meant to reach the widths without either widening
its signature or coupling the value type to ambient state. `NAMES.md` fixes the signature;
`PLAN.md` fixes the requirement the signature can't satisfy on its own.

**Why it matters** — S2/S3 wire `BoardCoord` into `GameData`/`Board`, and every caller of
`step_x` has to match whatever signature the owner rules on here. Shipping with the wrong
shape now means every call site written against it in later steps has to be revisited.

**Options I can see** — **(a)** the parameter as shipped, `step_x(n, grid_widths)` — matches
`PLAN.md`'s derivation requirement exactly, keeps `BoardCoord` a pure value type with no
outside dependency and fully unit-testable in isolation, but contradicts `NAMES.md`'s fixed
one-argument signature · **(b)** `step_x(n)` reading widths from ambient state
(`CardEnvironment.CURRENT` / `GameData.grids`) — matches the registry's signature, but couples
a value type to global game state, makes `BoardCoord` untestable without standing up that
state first, and makes the method's result depend on when it's called relative to game setup
· **(c)** `BoardCoord` carries a reference to the grid list (injected at construction or held
statically) — keeps the call site at one argument like the registry wants, but turns every
`BoardCoord` instance into something that must be constructed with, or discover, board
context, and raises its own question of how/when that reference gets set for coordinates
built before a board exists · *no recommendation stated here*

**Blast radius** — `Scripts/board_coord.gd`'s `step_x` signature; every future call site in
`GameData`/`Board` (S2/S3); `Tests/Engine/test_grid_board.gd`'s existing calls, all of which
use shape (a).

**Meanwhile** — parked: the final signature. Continued on: `step_x`'s arithmetic itself, which
is correct and tested under shape (a) regardless of which option wins.
