# GAP-003 — no fixed mapping from a legacy zone position onto `BoardCoord`

status: resolved
outcome: answered
raised: 2026-08-26, during execution plan step S3 (the position index)
design: NAMES.md §2 (`GameData.position_of`); PLAN.md §1.1
severity: GAP

## OWNER ANSWER — retire the legacy coordinate entirely

Owner, verbatim:

> *"Not sure what you mean here, but no reason to keep legacy version with 3 coords. Legacy
> version can just count as its own grid for the lower zone, while upper zone is now the moving
> entrance zone."*

The rule this produces:

- **There is one coordinate type: `BoardCoord`.** The legacy `Vector3i` board position is
  retired; `position_of` returns `BoardCoord` as `NAMES.md` §2 always said.
- **The legacy lower zone becomes its own grid** — an ordinary entry in `GameData.grids`, with
  no special case.
- **The legacy upper zone becomes the Entrance**, the moving zone at `y == ENTRANCE_ROW` of
  whichever grid it is attached to.
- So none of options (a), (b) or (c) is taken: there is no legacy mapping to invent, because
  there is no legacy representation left to map.

### Sequencing — the owner said WHAT, not WHEN; this is the overseer's call

Measured blast radius: **296 references to `upper_zone` / `lower_zone` across 29 files**, plus
`Board.locate`, `position_of`, and the board-position `Vector3i.MIN` checks. It reaches the UI,
the props and the pips, not just the engine. The plan schedules no such migration anywhere — it
assumed the two boards coexist.

**Scheduled as a new step, `S19b`, immediately after S19.** Reasons:

- Phases 2 and 3 (line detection, scoring, economy) operate **entirely on grids** — the design
  already says lines never cross a grid boundary — so they do not read the legacy
  representation at all. Deferring costs them nothing and wastes no work.
- S19 archives the tableau rules cards (the grabber, the placer, the cascade scorer), which are
  the lower zone's main operators. Migrating after that leaves far less to carry across.
- Doing it before Phase 2 would put the largest refactor of the run in front of the scoring
  work that the phase gates actually measure.

⚠ Until `S19b` lands, grid work reads the grid index (`card_at`, the grid forward index) and
NOT `position_of`, which still returns the legacy `Vector3i`.

⚠ This supersedes the provisional option (b) that S3 shipped — the grid index is no longer a
sibling of a surviving legacy index; it becomes the only index.


**What the design says** — `NAMES.md` §2 fixes `GameData.position_of(card)` as the "Existing
name, now returning `BoardCoord`." `PLAN.md` §1.1 fixes `BoardCoord` as `grid, x, y, h`, with
`grid` an index into `GameData.grids` and `x` a column continuous ACROSS grids.

**What the repo says** — through Phases 1-4 (S1-S19) the two boards COEXIST: the legacy board
(`upper_zone` / `lower_zone`, positions `Vector3i(x, col, row)` with `x` = 0 upper / 1 lower and
headers at row -1) does not go away until S17-S19. `position_of` today returns `Vector3i` and is
read at roughly 50 call sites (`Vector3i.MIN` checks) and 7 `Board.locate` callers.

**What it does not say** — how a legacy `(zone, col, row)` position maps onto a single
`BoardCoord`. A legacy zone is not a `GameData.grids` entry, so `grid` has no natural value;
`x` is specified as continuous across GRIDS specifically, not across the legacy zone and the
grids together. No document says whether upper/lower should be folded into the `grid` ordinate,
given a synthetic negative `grid`, or left unrepresentable until S17-S19 retires them.

**Why it matters** — picking a mapping now is expensive to reverse: every one of the ~50
`Vector3i.MIN` sites and 7 `Board.locate` callers would need to migrate to whatever shape is
chosen, and a wrong guess makes S4/S5 (which build directly on the position index) unreviewable
against a moving target.

**Options I can see** — **(a)** migrate `position_of` to return `BoardCoord` now, inventing a
mapping for the legacy zones (e.g. `grid = -1` for upper, `-2` for lower, `x` = legacy col,
`y` = legacy row) — matches `NAMES.md` literally today, but the mapping is invented here, not
decided by any document, and touches every caller in one step · **(b)** leave `position_of`
returning `Vector3i` for the legacy board unchanged until S17-S19 retires it, and add the
`BoardCoord`-typed reverse index (`card_at`) and a private grid-only forward index alongside it
— matches the coexistence the plan's own phasing implies, defers the signature change to the
step that actually retires the legacy board, but means `position_of` does not literally match
`NAMES.md`'s stated return type until then · **(c)** widen `BoardCoord` itself to represent a
legacy zone position (e.g. a `zone` field alongside `grid`) — keeps one coordinate type
everywhere from S3 onward, but `NAMES.md` §1 fixes `BoardCoord`'s four components exactly and
adding a fifth is itself a registry change nothing authorises

**Blast radius** — `Scripts/game_data.gd`'s `position_of`/`_scan_positions`; `Scripts/board.gd`'s
`locate`; every `Vector3i.MIN` off-board check; every step from S4 onward that reads a card's
board position.

**Meanwhile** — parked: `position_of`'s return type and any legacy-to-`BoardCoord` mapping.
Continued on: `_scan_positions()` walking grid cells, the grid-side forward index, the reverse
index (`card_at`), the stated invariant between them, and `validate()` checking it — all of
which needed no legacy mapping, per option (b) above, which this step implements provisionally.
