# GAP-041 — the board opens scrolled to the TOP; the anchor-to-bottom waits a frame count

status: resolved
outcome: answered by the owner — **the scrollbar defaults to the BOTTOM of its range**
raised: owner observation
design: DESIGN.md §36 flowchart H (`H13`), `Q313`=(a); the board's floor rule
severity: PRODUCTION CODE WAITING A FRAME COUNT INSTEAD OF FOR THE GEOMETRY TO SETTLE

## OWNER RULING

> *"scrollbar should default to bottom of bar, not top"*

Which is the right default for this board: the floor is at the bottom (`TopLevelVBox` /
`ALIGNMENT_END`), stacks grow UPWARD off it, and the Entrance sits below everything. **The bottom is
where the game is.**

## The mechanism already exists — it mistimes itself

`UI/play_area.gd`:
```gdscript
## Scroll to the bottom of the board. ⚠ ON ENTRY ONLY -- a rebuild that re-anchored would yank
## the view out from under a player who had scrolled somewhere else.
func _anchor_scroll_to_bottom() -> void:
	if not is_instance_valid(scroll_container): return
	await get_tree().process_frame
	var bar := scroll_container.get_v_scroll_bar()
	if bar: scroll_container.scroll_vertical = int(bar.max_value)
```
called once, deferred, on entry.

**It waits exactly ONE process frame.** But the same file records that the geometry does not settle in
one: *"several frames — panel positions, the shared width and the scroll range all settle
separately"*. So `bar.max_value` is read while the range is still growing, and the standing rule
finishes the story: **"the scroller clamps every aim against the reach it can see that instant"** —
the aim is clamped to a smaller range and the view never reaches the bottom.

⚠ **This is the repo's own testing rule, violated in PRODUCTION code**: *"A test must wait for the
geometry to STOP MOVING, never a frame count."* The same applies to anything that reads a settling
rect.

## What the fix must do

Wait for the **scroll range to STOP CHANGING** before aiming at it, rather than waiting a fixed
number of frames. ⚠ **Do not "fix" this by waiting more frames** — that is the same defect with a
bigger literal, and a frame count is a tunable literal in a source file.

⚠ **Keep the ON-ENTRY-ONLY property.** The existing comment states why: *"a rebuild that re-anchored
would yank the view out from under a player who had scrolled somewhere else."* Re-anchoring on every
rebuild would be a new bug.

⚠ **A VALUE SAFE TO READ PER-FRAME IS NOT SAFE TO CAPTURE ONCE** — a latched copy of a settling
quantity was poisoned forever once already in this stream.

## Why it is more visible now

`GAP-040` makes the play area track the picture height (636 -> 841 px), and the Entrance work changed
the strip's contribution, so the scroll range is larger than it was. A mistimed aim that used to land
almost at the bottom now lands visibly short of it.

## Blast radius

`UI/play_area.gd` (`_anchor_scroll_to_bottom` and its deferred call site), the board's opening view,
and any check asserting the initial scroll position.
