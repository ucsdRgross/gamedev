# GAP-001 — a ⚑gate option with no `→ next:` is both a hard error and required to parse
status: resolved
raised: 2026-08-01, during execution plan step S2 (the grammar module)
resolved: 2026-08-01 — the owner chose **(b)**: a warning, not an error
resolution: |
  `parseQuestionLine` warns by default; `strict: true` still throws, which is what PLAN §5.6's
  must-throw case exercises. The warning now reaches both people who can act on it:
  `npm run check` names the question and its line, and the design's card in the index carries an
  "N authoring warnings" badge (`registry.docHealth` → `GET /api/designs` → `web/index.mjs`).
  On the question screen an option with no preview renders **→ next: not described** in place of
  nothing at all — S5's share of the blast radius. Rendering nothing would have been
  indistinguishable from "no questions follow this branch", which is a different claim and a false
  one. `.claude/skills/flowchart-design/SKILL.md` states the rule for future authoring.
  `solatro/SPOTLIGHT_DESIGN.md` was not edited; QR8 is the one live warning.
design: `designloop/design/designloop/DESIGN.md` rounds 1–2 (2026-08-01), nodes B7a, B7b, Q17d;
        `PLAN.md` §5.1, §5.6, S2
severity: CONTRADICTION

**What the design says** — DESIGN §1 rule 5: "A question whose answer prunes others shows, per
option, what kind of questions follow." `PLAN.md` §5.1 turns that into a parser rule: on a `⚑gate`
question "every option **must** contain a `→ next:` clause, and the parser errors if one does not",
and §5.6 requires a test where "a `⚑gate` missing one (must throw)".

**What it does not say** — which rule wins when a real document breaks it. `PLAN.md` S2 is equally
normative in the other direction: `solatro/SPOTLIGHT_DESIGN.md` must parse **unchanged**, with
**zero errors**, and "if it does not parse, the grammar is wrong, not the document".

`SPOTLIGHT_DESIGN.md` line 875, QR8, is marked `⚑gate` and its option **(a)** carries no
`→ next:`; only option **(b)** does. Exactly one question in 196 breaks the rule. Both instructions
cannot hold: strict parsing gives one error and fails the acceptance gate, and a clean parse means
§5.1's "the parser errors" is not true.

**Why it blocks** — CONTRADICTION (the design says two incompatible things). It is also a GAP on its
own terms: the two choices differ in what the owner sees. Under (a) the tool refuses a document that
is 195/196 correct; under (b) a genuinely under-specified gate reaches the owner as a branch with no
preview, which is the exact failure rule 5 exists to prevent. It is expensive to reverse: it is the
strictness contract of the interchange format, and every design document written from here on is
authored against whichever answer is given.

**Options I can see** — **(a)** hard error, as `PLAN.md` §5.1 says — the acceptance document must be
edited to add QR8's missing preview, and the S2 "unchanged" clause is relaxed to "unchanged except
for defects the parser names" · **(b)** a **warning**, not an error — the document parses, the tool
shows the gate with only the previews it has, and the warning is surfaced to the authoring agent and
on the design's index card · **(c)** hard error, but only when the question has **no** previews at
all; a partially-previewed gate warns — the failure mode being guarded against is choosing a branch
completely blind, and one preview out of two still shows what the other branch is not ·
*my recommendation* (b) — the acceptance gate is the load-bearing requirement of Phase 0, and a
warning surfaces the defect to the person who can fix it (the authoring agent) without blocking the
person who cannot (the owner, mid-questionnaire)

**Blast radius** — plan steps S2 (grammar strictness), S5 (what the question screen renders for a
gate option with no preview), S10/`SKILL.md` (what the authoring rule tells an agent); design nodes
B7a, B7b, Q17d.

**Meanwhile** — nothing is parked. `parseQuestionLine` takes a `strict` flag: `strict: true` throws
(so §5.6's test exists and passes), the default collects the shortfall in a `warnings` array
separate from `errors` (so the S2 acceptance gate passes and reports the one known warning against
QR8 by name). Whichever option is chosen, the change is one default and the removal of the other
branch. `SPOTLIGHT_DESIGN.md` has **not** been edited.
