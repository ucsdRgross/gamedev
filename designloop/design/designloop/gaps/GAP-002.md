# GAP-002 — the whole-graph view has no connections to show, because charts never link to each other
status: open
raised: 2026-08-02, during execution plan step S12 (canvas render), reported by the owner on review
design: `designloop/design/designloop/DESIGN.md` rounds 1–2 (2026-08-01), nodes F2, F8, Q52, Q64;
        `PLAN.md` §6, S12
severity: GAP

**What the design says** — Q52's written answer asked for both halves: the chart picker "if I want
easy access to all charts and be able to focus on specific subcharts without needing to see the
entire graph", and the whole graph at once "**if I want to see all connections** and whole picture".
Both were built (S12). §6 then requires that "every chart's node IDs must share a prefix letter,
which becomes the chart ID".

**What it does not say** — what the whole-graph view shows when there are no connections BETWEEN
charts. Measured on both real documents today: `designloop/design/designloop/DESIGN.md` has 133
edges and **0** cross-chart, `solatro/design/spotlight/DESIGN.md` has 182 edges and **0**
cross-chart. The charts do refer to each other, but in prose inside a node's label — `A6 "owner
answers one question at a time — chart B"`, `D8 "… — chart E"` — 8 such labels in one document and
4 in the other. So the link exists in the design and does not exist in the graph.

**Why it blocks** — GAP: two defensible choices differ in what the owner sees, and one of them
changes `graph.json`, which §4.6 specifies and an implementation agent consumes. The owner's report
is that as built, "all charts view is worse than clicking through each chart individually, since
individual is instant focus and less clutter" — the view that was supposed to show all connections
is the one that shows none, and costs legibility for it. Whether a prose reference should become a
drawn edge is not a rendering detail: it decides whether the graph an implementation agent reads
claims a link the document never drew.

**Options I can see** — **(a)** leave the graph alone and change what the whole-graph view is for —
it is the poster (how big is this, which charts exist, where the NEW work is), the picker is the
working view, and the tool says so instead of promising connections that are not there · **(b)**
derive cross-chart links from labels that name another chart and draw them, distinctly (dashed,
chart-to-chart rather than node-to-node) — the whole-graph view finally shows the loop the design
actually describes, and `graph.json` grows a `links` list beside `edges` so the implementation
agent sees the same thing the canvas does · **(c)** derive and draw them in the canvas only,
leaving `graph.json` exactly as §4.6 specifies — the picture improves and nothing downstream
changes, at the cost of the canvas showing something no consumer of the file can see, which is the
one thing Q64=(a) and the no-mocks rule exist to prevent · **(d)** widen the §6 mermaid subset so a
chart may name a node from another chart directly (`A6 --> B1`), making cross-chart edges real
edges the author writes on purpose — most honest, and it means the existing documents are edited to
gain the links they currently only imply · *my recommendation* (b) — the reference is already
authored, in the label, by hand, in both documents independently; deriving it is reading what is
there rather than inventing it, and putting it in `graph.json` keeps the canvas and the
implementation agent looking at one artefact

**Blast radius** — plan steps S11 (ingestion, if links are derived there), S12 (the whole-graph
view), S14 (a frozen version records the graph, so its shape changes with it); design nodes F2, F8,
G2, Q52, Q64; `PLAN.md` §4.6 and §6.

**Meanwhile** — parked: nothing is derived and nothing is drawn between charts, so `graph.json` is
exactly §4.6 and the canvas is exactly what it was. The rest of the owner's review is done — the
duplicated gate reason, the unrendered markdown, the truncated chart names, the fold-away chrome,
the question traceability on nodes, and the colliding edge labels are all fixed and none of them
touch this thread.
